# H1 30→90→300 长度缩放与门禁处置

两模式各完成 300 次。preview 的 90→300 次净增 −48,860 B，dev 为 +707,532 B，均未触发预登记追加条件。轨迹存在明显起伏，**没有观察到稳定达到本次目标量级的晚段净增长图样；也没有证明所有增长都是一次性成本**。慢速持续项、晚发有界保留和运行波动仍不能完全分开，本次没有足以提出业务源码泄漏修复的因果证据。

处置是交付已经独立审计、完整 CI 通过的 warn-only PR，保留原比较值；提出启动增量与晚段趋势分开的影子校准方案，不根据这两个样本提高正式阻断阈值，不采用每个 PR 固定三进程×六窗口。最终结果文档的独立审计状态见文末。

## 固定实验与可回答的范围

实验依据 `6ab0dfd699b282e3cf9846abf5bc37fa17eafaf8`；被测运行源码是其诊断所用的 `97f38a0e787a4edcb35df4a59823bb1d106def67`，与 warn-only PR 分开。预登记提交 `f485ff7496116d101d3d5543db257776d558fd75` 的[方案](H1_LENGTH_SCALING_PLAN.md)固定了环境、指标、扰动假设和最多一次追加规则。

[CI 37900065144](https://github.com/catfish-xn/cat/actions/runs/37900065144) 使用 Node 22.23.3、Chromium 153.0.8010.12；preview/dev 各一个新进程，2 次预热后同页面连续 10×30 次，桌面 1440×1000、seed42/cannon，无快照。保留全部边界，30、90、300 为主要检查点。复用原派生驱动，原 30 行断言和旧上限保留；堆断言在收集十窗后执行，因此诊断退出码与是否存在可用完整数据须分别判断。

把两种模型写为 H(n)=常数+前置/有限保留+g·n+扰动，缩放主要约束 g。一个有限的正差值不能区分一次性保留与持续泄漏；一个晚段负差值也不证明没有增长项。实际可能同时存在编译成本、小额记录保留及波动，不应强迫所有字节归入同一个二选一原因。

## 保留链解释力

来源为原[同会话保留链报告](H1_CI153_RETENTION_ANALYSIS.md)、[七边界计数](evidence/h1-ci153-snapshots/boundary-counts.json)及 `retention-excerpt.json.gz`。使用同一快照口径计算：

| 量 | 核算 | 能说明什么 |
| --- | --- | --- |
| ResourceData 本体 | (196−61)×288=38,880 B | DevTools 网络记录实际累计 |
| ResourceTiming 本体 | (171−36)×136=18,360 B | 浏览器性能记录实际累计，另有 Window 根 |
| 两者合计 | 57,240 B/180 次=318 B/次 | 占快照 self-size 净增 1,323,038 B 的 4.33% |
| 恒速外推 | 300 次 95,400 B；90→300 为 66,780 B | 远低于本实验总堆分辨能力；外推不是新测量 |
| code 前置增长 | 首 30 次 +816,116 B；后 150 次 +187,772 B | 首段占 code 净增 81.3%；单位周期增长约下降 21.7 倍 |
| 后 150 次账面核算 | code 187,772 + 两类节点 49,608=237,380 B；同期快照净增 244,306 B | 97.17% 是有正负抵消的净变化核算比，不是因果解释比例 |

两条记录链可以是持续小额保留的来源，但已计节点不足以解释 MiB 级 H1 端点波动。它们没有完整 retained-size：URL、响应体、容器容量等未归因，所以也不能反过来用 57,240 B 给整条链设置上限。快照 self-size 与 Runtime.usedSize 口径、时点不同；最后一个旧快照窗口前者仍增 38,260 B，后者已降 250,260 B，不能跨口径相减得到“剩余泄漏”。

其他仍合理的解释包括 JIT 编译/反优化/代码回收、浏览器性能缓冲、DevTools 网络记录及所引用数据、异步清理与 post-GC 测量时点差异。已观察的 LongTask、LoAF、LayoutShift 计数平台仅限该会话。普通 Object/Array/closure 数量持平、旧 session 样本消失支持生命周期正常，但不排除常驻对象内部容量增长、未抽中的闭包或更晚发生的保留。总 JS 堆也不能替代 GPU、进程 RSS 等不同内存预算。

## 判别下限与规则

按预登记，A=H30−H0，B=H90−H30，C=H300−H90。后段扰动假设 E=1,572,864 B 来自有限历史轨迹的量级，**不是 95% 置信界或纯噪声真值**。条件平均速率区间为 [(C−E)/210,(C+E)/210]，单侧量级分辨率 7.31 KiB/次；平台与稳态增长在最坏 ±E 误差下分离需超过 14.63 KiB/次，本次目标取 16 KiB/次，后 210 次产生 3.28125 MiB 信号。

在固定 H90 为晚段起点、只取整 30 次窗口的方案中，300 是满足该目标最坏分离条件的最短总长度：270 次只留下 180 次晚段，16 KiB/次的信号为 2.8125 MiB，小于 2E=3 MiB；300 次留下 210 次才超过 2E。这是条件量级设计，不是已校准的统计功效保证。

- `C>E`：增长候选。检查分布是否持续而非单次阶跃，并按预登记仅追加该模式一个全新 300 次进程；重复晚段增长加对象/所有权证据才支持业务泄漏归因。
- `|C|≤E` 且晚段无加速或资源累计：与这 300 次内前置/有界成本加波动相容，报告条件上界 `(C+E)/210`。上界低于 16 KiB/次时，才说在上述假设下未观察到达到本目标速率的持续净增长；更慢持续项仍可能存在，不能确定各项占比。
- `C<−E`、晚段单窗绝对变化超过 E，或 H90…H300 按时间顺序累计峰谷回撤超过 E：扰动假设可疑，追加一次同模式复核；不把大幅回落自动当平台，也不提高 E 追求通过。
- 缺窗、身份不符、超时、功能/资源失败是不可判；保留全部首次和追加结果，不择优、不同模式不投票。

若要仅靠总堆区分 318 B/次与平台，在同样的最坏 ±E 模型下需晚段至少 9,893 次，且还要证明 E 在如此长的会话仍成立。故 300 次或增加三个短进程都不能声称排除了已知慢保留；对此更经济的是直接数对象/条目并验证所有权反事实。

## dot 三进程×六窗口方案的必要性

其三态语义有价值：证据不足应保留“待复核”，不能靠重跑择优消失。但现在尚无证据证明每个 PR 都需要固定三进程×六窗口，也没有已标注真阴性样本证明该方案的误报率。

设每窗恒定增量为 b、背景完全平坦。dot 指标 D=b，K=b，G=T=3b，故 D 被 K 包含；理想无噪声的单进程阈值是 b>L/3，即 preview 超过 341.33 KiB/30 次（11.38 KiB/次），dev 超过 512 KiB/30 次（17.07 KiB/次）。历史背景叠加中“128 KiB/窗触发阻断”不是普适检测下限。18 个相关窗口也不是 18 个独立进程样本。

三进程每模式共 540 次、旧实测约 90 runner 分钟，双模式约 180 分钟；本次单进程 300 次的两模式计时合计 75.4 分钟，必要时才做一次新进程确认。不同宿主与路线耗时不能当严格性能对照，但循环预算和固定三倍进程成本是明确的。后一种设计把预算放在可辨认的累积信号上；多进程则用于复现异常和宿主敏感性，两者作用不同。永久阶跃由 K 捕获只能说明有额外保留，不能仅因两次出现就命名为无界业务泄漏。

单纯提高 30 次端点阈值会同时放宽真实增长预算，无法分开启动与斜率。比如 preview 从 1 MiB 调到 2 MiB，只是让历史最大 2,015,536 B 以 81,616 B 余量通过；没有尾部分布依据，不能据此保证以后不再超限。若把阈值除以 30，2 MiB 对应约 68.27 KiB/次的无噪声持续增长量级，慢泄漏更容易漏过。

## warn-only 交付与后续校准

[独立小 PR #20](https://github.com/catfish-xn/cat/pull/20) 仅改变完整应用堆超限的处理：保留 dev 1.5 MiB / preview 1 MiB 与原始读数，写入 `heapGate` 并告警，后续功能路线继续。坏证据、资源累计、独立模块堆预算及耗时预算仍阻断。未改运行源码或 B6/B7/U3；临时诊断工作流不合入目标分支。

具体建议如下；只有第 1 项已实施于 PR #20，其余是可审阅方案，没有写入正式门禁或自动调度。

| 层次 | 比较值/长度 | 决策与新增成本 |
| --- | --- | --- |
| 常规 PR 启动增量 | 原 2 预热/30 次；preview 1 MiB、dev 1.5 MiB | 保留原值和超限告警，完整应用总堆这一项不阻断；原有功能/资源/证据完整性仍阻断。无新增浏览器测量成本 |
| 按需长窗影子校准 | 一进程/模式，30→90→300；90→300 的 210 次区间累计 C>1.5 MiB（等价 C/210>7.31 KiB/次，右侧为四舍五入量级） | 只作为增长候选，沿用本文其他无效/扰动分类与一次确认规则；不自动给应用贴泄漏标签，也不把它作为已校准的新阻断预算 |
| 复现与归因 | 仅异常模式追加一次 300 次，新进程 | 保留两次全部轨迹；持续净增再配对象/所有权证据决定最小修复。无触发时不固定增加三个进程 |
| 启动阈值数值校准 | 随既有 CI 归档 D，按源码版本、Chromium、mode、job/CPU 分层 | 候选阈值先冻结，再用后续保留样本核验；不把历史最大值加少量余量直接变成正式通过线 |

本次建议继续使用第 1 项，长窗作为排查内存相关回归时的影子诊断，不进入每个 PR 的必跑矩阵；保留“观察范围内无明显趋势 / 增长候选 / 证据不足”的诊断语义。这个三态分类不改变用户已授权的 warn-only 合并政策；损坏证据和资源回归仍由原阻断项处理。

不建议现在把 preview 改为 2 MiB、2.5 MiB，或把 E 直接转成正式阻断阈值。旧 12 个正常样本及本次两个长窗没有给出可靠的启动尾部分布或独立无泄漏真值。若将来要求“超限概率不高于 5%”之类统计目标，必须事先选择目标、冻结阈值并使用独立保留样本；即使理想独立同分布且观察到零超限，至少 59 个样本才使单侧 95% 二项上界低于 5%，还不是业务泄漏的误报率。可以利用未来已有 CI 的匹配样本，不为凑数字在本轮新增 59 次运行。

若要恢复完整应用堆的自动阻断，应先在**届时接受的集成源码**上验证候选（本次固定旧源码不能替 B5/B6/B7/U3 签收），并用明确保留速率的独立诊断正控验证实际检出能力。16 KiB/次是本实验检测目标，不是用户已经接受的泄漏预算。对于已知慢链，最便宜的下一项因果检查是对象/性能条目计数及所有权对照；例如在独立扰动组比较清理性能条目前后，检验 NetworkResourcesData 是否仍保留，不能声称一次 clearResourceTimings 就修复所有根，也不能把该扰动组混入本次无快照轨迹。
