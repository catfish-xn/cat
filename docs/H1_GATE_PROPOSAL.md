# H1 门禁修复候选与现有数据回放（未实施、待用户决定）

## 建议

不要把“3次取中位数全过”直接当成修复。建议下一修复任务评估**三进程、六窗口、三态判定**：使用趋势信号，同时保留突增保护；孤立异常进入复核而非直接刷重跑变绿。此方案可能减少自动硬失败，但会增加测量成本及复核负担，不能宣称误报已清零。先影子验证，再由用户决定是否替换原门禁。

## 明确方法与判定

- preview/dev分别运行3个新浏览器进程，固定目标SHA、Node/Chromium、负载、viewport和原post-GC协议；每进程2次预热、6个等长窗口，每窗30周期，无快照。原功能测试仍保留。三个进程可独立runner并行，统计按mode/CPU/job分层。
- 保持L：preview=1,048,576 B；dev=1,572,864 B。H0…H6为7个post-GC边界值。
- D=H1−H0（启动段）；G=median(H4,H5,H6)−median(H1,H2,H3)（晚段水平变化）；T=H6−H3（尾端净增）；K=max(Ht−H(t−1))（任一窗口突增）。
- 单进程任一D/G/T/K严格大于L则hit。3进程≥2 hit自动阻断；1 hit为“待复核，不得自动放行”；0 hit仅通过当前负载/有限窗口，不证明永不泄漏。超时、缺数据、版本不一致不是通过，保存异常证据。
- 复核仅检查原始窗口、资源计数与必要保留链，不能通过不断重跑择优消除异常。未解决复核项不能被当作自动阻断命中或自动通过。
- 当前预览六窗实际每进程约30分钟，3进程串行约90分钟运行量，独立并行仍有3倍计算量；dev成本需本轮既定覆盖结束后注明。

## 为什么不用更简单的中位数规则

- DG（仅启动D与稳健G）会漏掉第6窗才出现的任意大永久阶跃；T保护尾端。
- DGT仍会漏掉第2窗开始、此后一直保留的任意大阶跃，因为前后中位数和H3/H6都已抬高；K补上这一盲区。
- K也会捕捉单窗波动，增加复核负担；因此不能把此方案包装成“自动通过更多且完全不漏”。永久阶跃表示明确保留增量，不自动等于无限泄漏。

## 固定合成保留增量的条件敏感度

仅在已有3条轨迹上作数学叠加，没有改运行代码、没有新增CI负载。固定5种形状及L的0、1/16、1/8、1/4、1/2、1、2、4倍；零量用作背景，不计入正增量场景数。线性/晚发线性/阶梯的量为每30周期保留字节（阶梯为平均），永久阶跃的量为一次保留字节。

表内“阻断”≥2 hit，“复核”1 hit且不自动放行，“放行”0 hit。数字是预先选择网格上的结果，不是普适检出下限。

- 35个正增量数学场景：DG为14阻断/4复核/17放行；DGT为16/5/14；DGTK为19/5/11。**11/35不是实际漏报率**：场景没有概率权重，小额保留并不自动构成阈值意义上的故障，有限阶跃也不必然是无限泄漏。
- 例如线性每窗128KiB在此网格会自动阻断；64KiB只进入复核。晚发线性及阶梯平均每窗512KiB才在此网格达到自动阻断；较慢/较晚的保留仍可漏过有限窗口。
- 背景本身可能含真实缓存/代码增长，既可能帮助也可能掩盖注入信号；叠加不模拟新增对象对GC/JIT的反馈。三轨迹统一叠加也偏向可复现故障，不能外推间歇性泄漏的检出率。
- 只在1个进程发生的真实异常最多进入复核而非自动阻断；若将复核改成仅提示后自动通过，应如实计入自动阻断漏检风险。
