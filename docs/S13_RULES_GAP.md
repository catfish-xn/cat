| 编号 | 决定 |
|---|---|
| P-F1 | 每个**在场上**的杰斯都有一座锻炉；杰斯在备战席、被卖或被消耗合星时，锻炉不显示。 |
| P-F2 | 初始位置不变：杰斯身后一格（己方视角行号 +1，最后一行封顶），被占用时按原有顺序找空格。 |
| P-F3 | 锻炉只能拖到己方区域的空格，不能进备战席，不能卖，不能装备，不占人口（`summon.countsTowardPopulation=false` 不变），也不是阵容单位，不进奖池，不占单位编号。 |

| P-F5 | 锻炉占格：其他单位可以放到锻炉所在格（不交换）。之后锻炉落到离保存位置最近的空格，规则同虚空生物（`nearestItemCell`）。 |

### 2.3 最小命令与合同改动

复用 `equipItem(state,itemId,unitId,slot)` 和线上 `equip`：空槽按旧装备逻辑；目标槽是一件永久普通组件、输入也是库存普通组件时，原子执行合成，产物留在目标槽。两库存组件仍由原 `combineItems` 处理。不跨两个单位抽装备、不隐式免费拆卸、不替换现有成装。

拟定成功顺序：先按移除两组件后的最终槽位集合验证配方/唯一性/独占，分配一个新永久物品 ID，记录 `itemCombined`，记录 `itemEquipped`，再规划产物所需临时装备。失败返回原 state、空事件，不消耗 ID/RNG；配方非法用 `invalid-recipe`，非组件占槽仍用 `item-slot-occupied`。两拳套→窃贼必须独占三槽；持有其他永久物品时 `exclusive-slots`，不能默默挤回库存。预览与执行共用校验、无随机抽样。

合同同步点：§15.1 矩阵；§15.2 删除“battle 目标仅备战席”的装备限定；§15.3 阵容锁改为只限制部署/出售和战中升星参与者；§15.5 扩展 equip 的合成结果/失败原因；补 `MATCH_CONTRACT`、装备预览/事件合同及来源账本规则。现有 wire 命令字段可复用；若加入权威“下场生效”投影字段，纳入 §14 白名单，不下发整个冻结输入。

### 2.4 冻结边界与结算

1. PvE `combatInputBasis`、当前 Combat；PvP 两方 `PlayerBattleSnapshot/BattleInput`、镜像源快照，在开战时深拷贝冻结。装备操作只写 **latest live seat** 的永久资产、装备随机记录和 Match 事件，禁止修改当前 HP/护盾/属性/触发器/战斗随机流。
2. 战中已上场单位仍使用旧装备直到本场结束。原物品在运营层被合成/重铸消费，也不能从冻结输入抹去；必须能按 `provenancePrefixLength` 重建旧物品身份。恢复不能要求冻结装备集合等于最新库存。
3. 不重编译已锁 live seat 的当前战斗，不重抽 battleSeed，不用下一场装备修订本场结果、伤害或回放。跨冻结边界同时到达的命令由服务器单写队列线性化：先提交则入本场，后提交则下场。
4. `frozen` 与整轮结算提交仍是不可交错事务。客户端不在整段战斗展示装备禁用；边界期间请求等原子事务完成后按原 round/revision 校验，过期明确拒绝并刷新，不改参数自动重放。不许以“永不锁定”为由插入半冻结事务。
5. 结算在最新 live seat 上应用本场合法成长和唯一奖励；不能用 resolver 的战前整份 Match 覆盖期间装备。战后升星按已有 survivor 规则搬迁 **最新** 装备，原先战斗中的死亡不删除永久单位；新装备不追溯获得旧战斗的装备计数/触发收益。
6. 窃贼手套沿已有独立 equipment 流，只为新父实例规划一次；读预览/重连不抽。合成/装备不能消费 loot、shop、battle RNG，拆卸同一个父实例再装备不刷出新一组本轮子项。当前战斗继续使用冻结子项。
7. 界面可读运营装备和“本场使用装备”两个明确来源；本场属性/回放来自 CombatView，不能把 live 新装备加进本场伤害显示。只定义这些数据和生效提示，不限定 UI 布局。

单人战中扩权需要重点修正 `resource-provenance.ts` 当前 combat-growth suffix 只接受升星/掉落的约束；否则加入战中合成后可能能玩却不能恢复。必须验证新合法事务，不可删除整个来源校验。PvP/PvE、单人/联机四路径都覆盖。

### 4.3 随机、来源和掉落

## 5. R5：野怪同伴死亡回血

### 5.1 现状与来源

S6 的 `TFT_Krug.ability.desc` 为：“Passive: Heal to full Health whenever an allied Krug dies.” 这是 **石甲虫专属 H 语义**。能力变量为空，不能编造一个来源百分比字段；“回满”可表示治疗需求为自身当时缺失生命的100%，但重伤交互和同 tick 时序并不在原档中。

原候选静态 HP=1200、AD=110、AS≈0.8、护甲50、魔抗25；这些也不能直接当作当前项目遭遇值。现行 `content/neutrals.ts` 的石甲虫为 **400HP、30AD、AS8000Bps、双抗20**，`stone-salvage-project-v1` 为 `missingHpBps=10000,maxReactions=2`。ENCOUNTERS §5 已规定同 encounter/同队/同族的正式死亡触发，下一 tick 正常治疗阶段执行，受重伤，不能复活同批已死者。

其他来源：狼是开场跳后排，鸟是同族死亡加攻速，龙/先锋是各自攻击或开场能力；**“野怪每死一只，其余所有野怪回满血”未找到来源。** 不把石甲虫机制推广到小兵、狼、鸟。

### 5.2 建议、影响范围与工作量

建议保持当前石甲虫规则，不改属性或所有怪的被动。无重伤时400最大HP、当前120，请求280→400；若重伤50%，同样请求280、实际140→260。第二个例子是现行项目 G06 规则，不是来源证明 TFT 原版一定如此。

推荐案规则版本/digest/旧档 **均无变化**；只澄清合同与提示。预计 **0.25–0.5 人日**复核现有向量/试玩证据；如发现实现缺陷，再按实际修改面估算。至少保留两只同 tick 死亡不复活、重复死亡通知不重复疗、下一 tick 目标先死则取消、重伤与恢复的验证。

### 10.2 推荐项目策略 P：2→1→0

推荐 `{ avoidRecentRounds: 2, fallbackOrder: [2, 1, 0] }`。history 每席按实际 PvP 轮从旧到新存储对手 sourceSeatId，一轮最多一条；PvE/选择/未提交重试不写、不占回避轮数。跨 stage 保留，淘汰对手条目仍占其原来的历史位置，但不能进入候选。不因掉线、重连或切 controller 清空历史。全轮唯一提交后原子追加一次；失败重试沿冻结配对，不再抽签或追加（**P**）。

局部候选 `C(s,k)` = 存活唯一 seatId 集合，减去自己，减去该席最后 k 个 PvP 条目中的 sourceSeatId，按代码点升序。依 fallbackOrder 取首个非空集合；不消费 RNG、不依赖输入数组顺序。存活小于 2、PvE、淘汰席、终局返回 `[]`。2 人只有唯一对手：必要时退到 0；3 人可能在 2 轮内遇完另外两人，先退到 1，不强制机械轮换；同一对手连续两轮时仍可能在 k=2 留有另一候选（**P**）。

**非空不等于能完成全房配对。** 准备期对全部存活席生成集合后，用同一确定性可行性检查规划全局退让级别；普通边必须满足双向成员关系。若没有覆盖全房的配对方案，整房试下一窗口；在每个窗口局部空集仍按上述顺序放宽。至 k=0 完全图保证有解。不允许仅因一次贪心洗牌失败便宣称无解；最多 8 席，可穷举/回溯验证（**P**）。

候选投影发布该全局级别的每席局部集合，可以是保守超集，不承诺每个元素都具有相同概率。冻结时只从可行方案抽签，普通边双向合法；实际 sourceSeatId 必在最后一次发布的本席候选中。准备期存活集合或已提交历史若变化，必须在冻结前先更新候选；不能先显示严格集合，再开战静默放宽到集合外（**P**）。

奇数 n≥3 时恰有一席打镜像，其余席两两真实配对。镜像源必须存活、不等于接收方、在接收方候选内；源席仍只参加自己的真实配对，不要求镜像边双向合法。接收方提交时记录 sourceSeatId；源方仅记录自己的真实对手，镜像被借用不额外添加历史。镜像的双边结算资格沿 §4/§9，不能给源方第二份结果（**P；历史细则 U**）。
