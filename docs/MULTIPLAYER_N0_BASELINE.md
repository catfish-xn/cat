## 4 任务如何划分

按依赖顺序分成 11 个可验收任务。规则与网络由 Codex 负责；正式界面依实施时的用户授权和 AGENTS 分工交给界面执行者。本轮不自动启动其他聊天或子代理。

| 顺序 | 任务 | 具体产出 | 完成判据 |
| --- | --- | --- | --- |
| 1 | T0 基线与合同 | 本报告、用户决定、联机合同草案 | 基线明确，重要未知被列出 |
| 2 | T1 服务端规则入口 | 引用现有源码的生产 Node 构建与验证入口 | 普通 Node 可跑，结果与基线一致 |
| 3 | TP 共享有限卡池 | 库存、商店占用、购买、刷新、升级、出售、淘汰和获取来源事务 | 极小库存与八席测试均守恒、无超卖 |
| 4 | T2 真实双方战斗 | 双方快照与身份映射 | A 的真实阵容与 B 的真实阵容在同一 Combat 中交战 |
| 5 | T3 双边结算 | 一份结果映射双方，收入、HP、成长和唯一收据 | 重复提交不重复扣血或发资源 |
| 6 | T4 八席状态机 | 卡池、回合、选择、PvE、配对、加时、淘汰和排名 | 无界面完整八席局通过 |
| 7 | T5 网络与投影 | 座位凭证、消息校验、命令顺序、回执、可见状态 | 两个测试浏览器操作同一八席房间且不越权 |
| 8 | T6 断线恢复 | 原席重连、旧连接失效、快照补发与事件游标 | 断线不重开局，不重复执行 |

T1 完成后，TP 与 T2 在接口稳定时可以分别推进；T4 必须同时等待卡池和双方战斗结算通过。不要让一个人改规则、另一个人未经合同直接假定服务器返回完整 MatchState。

每次只派发一个明确任务包或一个可独立检查的子任务。交付只需说明改变的行为、检查结果、剩余问题和下一项，不需要为每次提交重新索取确认。

6. 提供后续房间执行器需要的纯规则导出，不建设大厅、机器人或公共网络服务。
7. 运行相关类型检查、构建、一场已知战斗、拒绝命令和恢复检查；保存实际结果。

### 验收标准

- [ ] 独立开发位置明确，原 main 和用户文档保留。
- [ ] 普通 Node 执行生产构建，不依赖 Vite 开发服务器、Phaser 或浏览器全局变量。
- [ ] 固定输入下完整 state、events、RNG 与基线一致。
- [ ] 无效命令与旧 generation 不消费资源或随机数。
- [ ] 依赖同一份 simulation，未复制后分叉，也未删客户端目录。
- [ ] 没有引入联网、卡池或游戏规则变更来“顺便完成更多内容”。

已有探针仅是一场运行证据，不直接称为生产服务已完成。T1 的关键是把入口、构建与运行合同做成明确可维护的交付。

## 6 共享卡池使哪些任务变化

现有 generateShop 只接收随机状态、generation 和等级，没有全房库存；每格按费用概率后从同费英雄目录等概率选取。现有目录共 19 位英雄，按费用分布为 5、5、5、3、1。共享有限卡池因此不是“在网络消息上加一个字段”，而是新的房间资源模型。

必须在 TP 处理：商店里的未购买卡是否占用、锁店保留、购买转持有、刷新归还、升星的基础张数、出售与淘汰释放、开场与奖励来源、缺货回退，以及八席自然刷新顺序。这些操作要与金币、商店、随机数共同成功或共同失败。

仍沿用现有内容切片，不因共享卡池自动承诺完整赛季英雄。由于同费英雄种类少，竞争和成型速度会不同，首版试玩需观察；不可未经说明扩大每英雄份数来掩盖内容切片差异。
