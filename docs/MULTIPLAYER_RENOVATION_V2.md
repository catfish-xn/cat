# Set13 八人联机整改实施方案

日期：2026-10-12，Asia/Taipei  
版本：v2.1  
状态：N0 基线核查已开展；共享有限卡池与 PvP 加时已由用户确认  
目标：服务器权威运行的八人对局，真人不足时由机器人补满八个席位，供少量好友使用  
适用硬件：现有 4 核 8G 服务器，首版先验收一个房间  
当前进度：已开始基线与合同工作；游戏代码、分支合并和部署均未启动

保留现有战斗规则、内容与可复用界面，新增真正的多人对局编排。先验证双方阵容进入同一场战斗且只结算一次，再接入八席房间、网络、机器人和正式界面。两个席位的测试只是开发检查点，产品目标始终是八个席位。

本方案取代 CC 原四份文档中的施工顺序、多人战斗接法和验收建议。原文保留作为历史参考；其中的代码示例不能直接作为已验证实现。本方案也不自动修改已有 M8 离线合同、性能预算或项目权限。

2026-10-12 用户补充决定：首版必须采用八人共享有限卡池；6-7 后继续 PvP 加时。新增 N1P 和 TP 卡池任务，后续房间与机器人须遵循共享库存。执行现状见 [N0 基线与任务划分](MULTIPLAYER_N0_BASELINE.md)，接口草案见 [联机合同](MULTIPLAYER_CONTRACT.md)。

## 1 已确认目标与首版范围

### 1.1 已确认需求

- 每局开局固定八个席位，由 1 至 8 名真人与 7 至 0 名机器人组成。
- 玩家各自管理经济、商店、棋子、装备和选择，按房间统一节奏参加对局。
- 服务器校验操作，计算战斗、奖励、扣血、淘汰和排名。
- 浏览器发送操作意图，接收允许看见的状态和战斗结果，负责交互与表现。
- 人数不足时能正常开始，机器人应能独立完成整局，不要求高级策略。
- 支持几个好友在不同电脑、不同网络上进入同一私密房间。
- 使用现有 4 核 8G 服务器作为首个部署目标，不先建设大规模公共匹配平台。
- 首版使用八人共享有限卡池；6-7 后继续 PvP 加时直到决出最终名次。

### 1.2 首版交付边界

| 必须具备 | 首版可以简化 | 后续增强 |
| --- | --- | --- |
| 创建和加入私密房间，开局八席 | 邀请码和座位凭证，不必完整账号系统 | 账号、好友列表、公共匹配 |
| 双方真实阵容对战，双边正确结算 | 先复用现有有限英雄、羁绊与 44 件装备内容 | M9 内容扩充和赛季完整复刻 |
| 八人共享有限卡池，真人与机器人共同争夺 | 沿用现有英雄目录，独立配置每英雄份数 | 随后扩充英雄目录 |
| 补位机器人完整参与经济与战斗 | 一个基础难度，规则策略即可 | 多档难度、阵容识别、针对性站位 |
| 统一回合、选择截止、配对、淘汰与排名 | 首版配对可采用可复现的简化规则 | 更接近原游戏的复杂配对策略 |
| 短暂断线后恢复原座位与当前状态 | 活跃房间保存在服务器内存 | 服务器进程重启后的无缝续局 |
| 公开阵容查看、当前战斗播放、结果与排名 | 不要求独立回放文件导出与任意历史 seek | 回放分享、历史战绩、排行榜、聊天 |
| 目标服务器上一房间可玩 | 不承诺 20 至 30 房间并发容量 | 容量扩展和多房间调度优化 |

首版不以客户端上传的金币、胜负或旧本地存档恢复在线状态。现有离线功能在迁移期间保留为回归依据，不建设第二份长期维护的规则实现。

服务器进程重启与浏览器断线分开处理：前者在首版可以使对局明确中断，不能伪造排名、补发不确定奖励或让客户端以为原局仍在继续；后者必须能够在服务器仍存活时恢复原座位。这一简化减少了首版数据库与崩溃恢复工作，不减少正常联机正确性。

## 3 新架构的职责边界

### 3.1 一份规则源码与三个执行边界

| 层次 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| 纯规则核心 | 买卖、装备、成长、经济计算、战斗 tick、明确输入下的结果 | 网络连接、真实时钟、身份、数据库、界面 |
| 服务器房间 | 八席资产、命令顺序、回合与截止时间、双方快照、结算提交、排名、可见投影 | 视觉布局、动画速度 |
| 浏览器会话与表现 | 发送意图、展示本玩家与公开数据、播放事件、显示等待与断线状态 | 决定权威金币、随机数、战斗推进或胜负 |

服务器与必要的离线工具引用同一份纯规则源码。可新增构建入口或共享模块边界，不复制一份 simulation 后让两边独立修改，也不做全目录字符串替换来“修复”导入。

在线客户端可以暂时保留只读类型、静态内容和旧离线入口。真正要切断的是在线路径对权威命令和 stepMatch 的本地调用；无须为了删文件而重写整个界面。

### 3.2 建议的状态模型

这些是需要实现的设计对象，不声称仓库已有同名类型。

| 对象 | 核心内容 | 唯一负责人 |
| --- | --- | --- |
| RoomState | roomId、版本、八席、共享卡池与占用账本、当前轮次、阶段、截止时间、配对、排名、roomRevision | 房间状态机 |
| SeatState | seatId、真人或机器人、连接状态、资产、商店、HP、经济与选择状态、seatRevision | 房间内该席位的命令事务 |
| ConnectionSession | 凭证、已绑定席位、connectionEpoch、最近回执 | 网络入口；不混入战斗核心 |
| BattleInput | 双方可信阵容、效果、单位映射、规则版本、独立战斗随机输入 | 服务器冻结，开战后不可变 |
| BattleResult | battleId、结果、双方存活者、成长与完整事件、必要的结算依据 | 一次战斗计算 |
| RoundSettlement | roundId、所有战斗结果、八席经济变化、淘汰与唯一提交标记 | 房间统一提交 |
| PlayerView | 本席私有信息、其他席位公开信息、可播放的公开战斗数据 | 服务器白名单投影 |

不同时维护可独立修改的 player.hp 和 player.state.playerHp。迁移期允许适配旧结构，但必须指定权威字段，另一处只能派生；回合和终局状态同理。

### 3.3 一次真实对战的完整路径

1. 准备截止后，房间冻结 A 与 B 的合法阵容及其全部效果。
2. 将双方单位、装备、强化、异常、持久成长映射为单场战斗输入；单位和效果来源身份不能碰撞。
3. 运行一个 Combat。A 和 B 分别看到自己的视角，但权威结果只有一份。
4. 把战斗中的局部阵营映射回真实席位，生成双方结算提案。
5. 汇总本轮所有战斗结果后，提交一次房间结算，计算淘汰与排名。
6. 向各客户端发送各自可见的数据。动画播放、页面隐藏和本地回放不改变结果。

PvE 仍是玩家对中立敌军，并按目录处理，不强行套为真人配对。满八席的 PvP 通常是四场实际对战；满八席的 PvE 则可能需要八场独立战斗，服务器负载测试必须覆盖两者。

八人联机与机器人补位已经确定。以下默认方案用于形成可实施合同；涉及玩法取舍的项目在 N0 集中定稿，不能由实现者默默替换。无需为了本次写文档逐项等待确认。

| 编号 | 事项 | 建议首版规则 | 定稿影响 |
| --- | --- | --- | --- |
| D1 | 商店与卡池 | 用户已确认：首版使用八人共享有限卡池 | 增加 N1P／TP；商店占用、刷新、购买、升星、出售、获取奖励和淘汰归还统一做房间资源事务 |
| D2 | 回合内容 | 保留现有开场、PvE、补给和选择节点；目录中的 PvP 替换为真人或机器人席位对战 | 不能删除野怪、强化和掉落来换取“能联网” |
| D3 | 6-7 后仍多人存活 | 用户已确认继续 PvP 加时；建议沿用最后已定义阶段的基础伤害与经济，不凭空新增奖励或强化 | 加时参数与平局规则写入联机合同，不继承单人 6-7 自动终局 |
| D4 | 开始和补位 | 房主明确开始；所有已加入真人准备后补满八席。开局后不新增真人参赛 | 防止第一位玩家刚点准备就启动；房主离开等待房时转交最早加入者 |
| D5 | 准备与选择时限 | 普通准备默认 30 秒；选择节点使用独立、明确的截止规则，默认 30 秒（海克斯在 50 秒准备阶段内选；早先 48 秒的设定已被 2026-10-23 合并准备阶段取代；原批准见用户 2026-10-23，覆盖原建议 30 秒） | 服务器决定截止；选项兜底不能额外花钱或重复发奖励 |
| D6 | 奇数存活者 | 为一名玩家分配另一存活者的冻结镜像；镜像只影响受测玩家，不反向扣原主 HP 或发原主奖励 | 不能与自己镜像对战；来源选择和避免重复规则应可复现 |
| D7 | 平局与同时淘汰 | 平局双方按合同扣血；同轮淘汰按扣血后未截断 HP、轮前 HP、固定席位次序依次破同分 | 批量定排名，不能由结果到达顺序决定；全员同时归零也需唯一终局排名 |
| D8 | 断线与离开 | 断线保留席位，建议 60 秒后由基础机器人临时接管；本人凭证重连后在安全操作边界接回 | 已消耗资源不撤销；准备截止仍执行合法兜底；开局后主动离开也不直接删除席位 |

联机伤害应从选定基线的正式数值与规则提取，再说明双方映射和平局差异。不得直接采用 CC 示例中的“stage + 2”并称为原规则。

D3 的加时方向已经确认；其参数及 D7 定稿时，应说明零存活者时由同轮排名规则产生第一名，以及为何这不是单人终局判断。加时必须有可论证的结束条件：真实对战失败或平局持续减少 HP，不能因为所有人平局而无限循环。异常超出验证的轮次上限时明确报错结束，不伪造正常胜利。

不因网络改造顺便提高英雄数量、改装备平衡或引入新游戏模式。确有规则变更时，更新联机协议和规则版本，保留旧离线合同适用范围。

## 5 命令与同步合同

### 5.1 命令入口

客户端仅提交买卖、刷新、经验、站位、装备、选择、准备、离开等意图。不得提交任意 MatchState、金币、HP、胜负、战斗 tick 或服务器随机流。

每条请求至少携带协议版本、roomId、commandId、目标轮次或阶段标识、相关资源版本及动作参数。实际操作者由连接绑定的席位取得，不信任请求中的 playerId。

房间整体变化使用 roomRevision；本席资产使用 seatRevision；购买仍保留 shopGeneration，选择保留 choiceId 与 generation。不要让其他玩家的无关操作使本玩家全部请求过期。具体命令需要哪些前置版本，由协议表逐项定义。

处理顺序为：解析与字段校验 → 身份和席位 → commandId 去重 → 阶段及资源版本 → 现有规则校验 → 成功事务提交 → 记录回执 → 发送投影。失败不消费资产、随机数或事件序列。

共享卡池和该席位资产必须在同一事务提交，失败时库存、占用、金币、商店、随机流和版本均不变化。客户端不必因为另一玩家改变了库存就全部重发请求；服务器按最新库存串行裁决，并返回明确回执。

每房间只有一个逻辑写入者。异步计算可以放到工作线程，但提交状态仍按房间顺序进行。战斗开始、结果返回和断线接管都应携带所属轮次与执行代次，拒绝迟到的旧任务。

### 5.2 去重与反馈

- commandId 在本局和席位范围内唯一；相同编号、相同内容重试返回原结果。
- 相同编号却内容不同，拒绝；不能当新操作再扣钱。
- 对成功、失败和等待分别反馈；客户端没有回执时显示待确认，不能冒充已成交。
- 去重历史有明确保留规则。已过保留窗口的旧请求必须拒绝并要求重同步，不能忘记编号后重新执行。
- 断线期间不无限积压购买或站位；重连时先恢复状态，再处理仍然适用的未确认请求。
- 服务器内存丢失后，旧局明确中断，不承诺跨进程重启的同局去重恢复。

### 5.3 数据可见性

| 数据 | 本席客户端 | 其他玩家客户端 | 服务器 |
| --- | --- | --- | --- |
| 本席商店与待选项 | 可见 | 默认不可见 | 完整 |
| 公共 HP、等级、排名、阵容 | 可见 | 按观战合同可见 | 完整 |
| 装备及已公开效果 | 可见 | 按公开阵容合同可见 | 完整 |
| 随机流、未来掉落计划、内部来源上下文 | 不发送 | 不发送 | 保留 |
| 已发生战斗的公开结果与表现数据 | 按对战或观战权限发送 | 按权限发送 | 完整账本 |
| 重连凭证 | 仅本人持有 | 不发送 | 校验凭证或其安全摘要 |

用白名单构造 PlayerView，而非把完整 MatchState 序列化后零散删字段。已有 LCG 状态和种子存在可预测及派生关系，不能因为字段叫 battleSeed 就认为可公开。首版客户端播放公开事件和快照，无需下载内部随机种子重算胜负。

### 5.4 时钟与断线

服务器维护准备、选择、战斗与结算阶段。客户端倒计时只是显示，浏览器后台、暂停或倍速不能推进或暂停权威对局。

每批数据带房间版本、轮次、battleId 与事件游标。重连后，在同一版本边界先发当前可见快照，再发连续增量；游标缺口无法补齐时重新发快照。不得重复播放为新结算。

凭证绑定 roomId 与 seatId。重连增加 connectionEpoch，使旧连接不能继续有效发操作；邀请码用于加入房间，不能直接作为座位身份。

等待房断线、开局后断线、淘汰后断线分别处理。开局后席位、资产、配对历史和名次不能随 WebSocket 关闭而删除。

| 阶段 | 主要产出 | 最重要的通过条件 | 前置依赖 |
| --- | --- | --- | --- |
| N0 基线和规则定稿 | 固定源码、差异表、八席规则合同草案及定稿项 | 不再存在会改变核心架构的未说明假设 | 无 |
| N1 规则服务化入口 | 共用源码的生产 Node 构建与运行入口 | 脱离浏览器运行且既有行为一致 | N0 的源码基线 |

| N2 真实双方战斗 | 双方快照适配、一次战斗、双边结算提案 | A 的阵容确实影响 B 的结果，双方效果生效 | N1；相关规则已定稿 |
| N3 八席房间状态机 | 卡池整合、配对、PvE、选择、截止、结算、淘汰、排名 | 无界面运行完整八席流程 | N1P、N2 与 N0 玩法合同 |

每阶段形成可检查的产物，不把每个小步骤都变成用户审批。只有改变目标、规则取舍、既有验收要求或发布承诺时，才需要用户作出相应决定。本次文档写入不授权执行这些阶段。

## 7 分阶段任务与验收

### N0 基线和规则定稿

**实施内容**

1. 确认真正的项目目录、Git 工作树和未提交改动；记录原状态。
2. 固定候选 SHA，列出纳入和未纳入的 M8 修复及已知失败。
3. 按第 4 节形成规则差异表；集中处理会影响架构的选择。
4. 列出线上命令、阶段、公开信息与失败语义；区分单人旧合同和联机新合同。
5. 定义后续阶段的负责文件与验证入口，遵守实施时的用户授权和 AGENTS 分工。

**交付物**

- 基线记录与差异清单。
- 联机规则合同、命令和投影合同；必要时可先合并成一份 MULTIPLAYER_CONTRACT.md，避免重复维护。
- 待定项清单，注明影响哪个阶段，不混入已批准规则。

**验收标准**

- [ ] 源码和历史失败可定位到固定版本，没有丢失用户改动。
- [ ] 已确认八席、真人数、补位时点、各类回合和终局策略。
- [ ] 没有把两人技术验证改写成最终两人产品。
- [ ] 对 D1 至 D8 有明确结论或有界待定项，实施者无需自行改玩法。
- [ ] 未因规划阶段执行合并 main、部署或暂停实验的重新启用。

**发现问题时**

工作树状态不明先解决定位，不覆盖或清理。规则意见不一致时只暂停依赖该规则的部分，继续源码核查、构建准备等独立工作。

### N1 规则服务化入口

**实施内容**

1. 新增普通 Node 可运行的构建入口，引用同一份纯规则源码。
2. 明确实际构建方案，处理省略扩展名、JSON 和运行时依赖；不能只证明开发运行器可启动。
3. 保持纯规则不依赖 DOM、Phaser、网络与真实时钟。
4. 在服务外壳中建立可注入时钟、显式随机输入和有界计算执行接口。
5. 新测试与既有测试分开命名，保留已有接口和离线路径。

**验收标准**

- [ ] 生产构建产物能由普通 Node 启动，运行一场已知战斗；不依赖 Vite 开发服务。
- [ ] 固定输入的 state、events、RNG 与选定基线一致。
- [ ] 无效购买、旧商店 generation 等失败不消费资源或随机数。
- [ ] 服务构建闭包没有误导入浏览器入口。
- [ ] 同一份规则源码供两侧需要的入口使用，没有长期复制分叉。
- [ ] 相关类型检查、构建和领域回归通过；历史已知失败单列。

**证据与回退**

保存构建命令、实际 Node 版本、源码标识和最小运行结果。若生产入口不成立，修改构建边界，保留旧入口；不得为让 Node 启动而批量重写全部导入或删校验。

### N1P 共享有限卡池

**实施内容**

1. 定义按英雄区分的有限库存及占用账本，真人和机器人使用同一个房间卡池。
2. 商店生成时占用库存；购买把商店占用转为持有，不能再次扣一份。
3. 刷新归还未购买的格子后重新抽取；锁店保留占用，换轮刷新按合同处理。
4. 升星保留对应基础张数；出售和淘汰按来源释放，避免一张二星只归还一份。
5. 把开场赠送、野怪奖励和其他英雄获取纳入同一来源与库存合同；镜像和召唤物不制造实体卡池份数。
6. 抽卡按现有等级费用概率和同费剩余份数进行；缺货时的费用层回退及空格行为显式定义。
7. 使用跨席位的原子事务，房间串行执行，并保留明确的随机消费语义。

**验收标准**

- [ ] 每英雄可用量加商店占用加持有量及合法待领取占用始终等于初始份数；没有负库存。
- [ ] 两席争夺最后一份时不会超卖；重复购买或刷新不会重复消耗。
- [ ] 锁店、刷新、出售、二星与三星合成、淘汰归还均维持守恒。
- [ ] 金币不足、备战区不足、旧 generation 等失败不改变任何卡池或资产字段。
- [ ] 所有席位同时自然刷新有可复现的顺序，不能永久给 seat0 抽卡优先权。
- [ ] 开场和掉落单位有明确来源；测试涵盖缺货、待领取、放弃和终局释放。
- [ ] 淘汰重复处理不重复回池；对战镜像不占池、不回池。
- [ ] 相同房间输入与命令顺序可复现商店，旧单人无限商店合同不被暗改。

**证据与回退**

先用极小库存夹具验证守恒和冲突，再接现有英雄目录。缺货规则或数值尚未核实时，不把猜测配置标为正式；T1 的服务构建可以独立继续。

### N2 真实双方战斗

**实施内容**

1. 设计 PlayerBattleSnapshot，承载一方真正拥有的上场单位、装备、强化、异常和成长。
2. 实现双方编译器，映射坐标、局部阵营、单位 ID、装备 ID 和效果来源。
3. 新建受信的多人战斗入口，保持旧单人入口的适用范围。
4. 计算一个 BattleResult，生成双方结算提案；此时可以用两个测试席位验证，不先做大厅。
5. 处理正常胜负、平局、空阵容、时间上限、成长回写和重复结果。
6. 为新输入建立相应版本与恢复校验，不能关闭旧恢复校验后硬塞真人敌军。

**验收标准**

- [ ] A 和 B 的真实单位同时出现在同一战斗，替换 B 的强弱阵容会按独立预期影响 A 的结果。
- [ ] 至少一组已知答案的简单战斗，以及包含装备、羁绊、强化、异常和持久成长的代表性组合通过。
- [ ] 双方均可持有同种装备、相同原始 unit 编号，仍不会串所有权或覆盖来源。
- [ ] 同一 battleId 只有一份权威结果；双方结果和扣血映射相互一致。
- [ ] 同一结果提交两次不会重复扣血、发钱或累加成长。
- [ ] 交换双方位置或视角后，身份和效果映射正确；确定性平手顺序按合同验证，不武断假设所有换边结果完全对称。
- [ ] 原单人战斗与恢复规则没有因引入多人入口被破坏。

**证据与回退**

保存双方输入、单位映射、预期与实际结算、完整事件及重复提交结果。若只能跑各自固定敌军，N2 不通过；继续修双方接口，不进入机器人调优。

### N3 八席房间状态机

**实施内容**

1. 从第一版房间模型固定八席并接入共享有限卡池；用测试驱动的席位操作贯穿回合，不要求先有聪明机器人。
2. 实现等待、选择或准备、冻结、战斗、结算、终局各阶段和合法迁移。
3. 房主开始时补满八席；开局后席位不可因连接断开而消失。
4. 区分 PvP、PvE 和无战斗补给回合，保留目录中的合法选择与奖励。
5. PvP 统一配对，处理奇数存活者镜像和避免不必要重复对手。
6. 冻结全部输入，再计算各战斗，最后统一提交本轮结果。
7. 根据 D3/D7 实现加时、平局、同时淘汰和完整排名。
8. 区分领域“战斗到时间上限而平局”与执行器崩溃；后者不能擅自判任何玩家输。

**验收标准**

- [ ] 开局恰好八席；8、7、5、3、2 名存活者时都能按规则配对。
- [ ] 无自战、无重复参与真实配对；镜像不反向修改原主资产与 HP。
- [ ] 满八席 PvP 的四场、PvE 的最多八场和无战斗轮次均有针对性测试。
- [ ] 刷新、选择、准备截止同时发生时，按统一事件顺序处理，不重复冻结或结算。
- [ ] 选择超时采用合法确定性兜底，空阵容、无目标、满备战区等状态不会卡死整房间。
- [ ] 某场计算失败不导致先到结果的玩家已扣血、其他玩家尚未结算的半轮提交。
- [ ] 多人同时归零的排名与结果返回顺序无关，名次唯一且完整覆盖八席。
- [ ] 单人 6-7 终局逻辑不会提前终止在线房间；联机终局有确定且可验证的结束条件。

**证据与回退**

采用可注入时钟运行阶段边界测试，不依赖真实等待 30 秒。计算失败可从原冻结输入进行有界重试；重复失败则明确中断房间并记录原因，不以无限重试维持“运行中”。

### N4 网络与恢复

**实施内容**

1. 提供创建、加入、准备、开始、离开和操作消息入口。
2. 服务端生成不可猜测的座位凭证；昵称和邀请码不能代替身份。
3. 实现运行时消息校验、版本检查、频率及大小限制，房间单写队列和命令去重。
4. 建立 PlayerView 白名单投影，发送版本化快照、回执与连续事件。
5. 实现断线检测、凭证重连、旧连接失效、补发或全量重同步。
6. 用两个独立浏览器测试客户端连接同一八席房间，其余六席由测试驱动补齐。
7. 定义界面所需的 Session 接口，使正式 UI 后续接入不再直接使用完整服务器 MatchState。

**验收标准**

- [ ] 两个浏览器各控制自己的席位，买卖或站位会反映到真实对战。
- [ ] 伪造他人 seatId、发送客户端金币或胜负不能改变权威状态。
- [ ] 非法字段类型、过期协议、旧商店、旧选择及已截止操作被明确拒绝。
- [ ] 重复请求只执行一次；相同 commandId 不同内容被拒绝。
- [ ] 同一房间其他玩家操作不会无理由让本席正常购买全部失效。
- [ ] 丢确认后重试、重复事件、应用层旧消息和游标缺口均不会重复扣费或结算。
- [ ] 断线再连接恢复原席位；旧连接不能继续操作。
- [ ] 抓取实际下发消息，确认没有其他人的私有商店、内部随机流和未来计划。
- [ ] 页面隐藏不暂停房间，断线也不触发全局新局。
- [ ] 此阶段只可声明网络验证通过，不能用测试界面宣称正式产品已经完成。

**证据与回退**

保存最小消息记录和故障注入结果，敏感凭证不进入报告。先用可见快照完成正确同步，不同时引入复杂增量压缩和客户端经济预测。

### N5 基础机器人

**实施内容**

1. 机器人通过与真人相同的合法命令入口操作，不直接写金币、装备或胜负。
2. 每次基于最新状态选择一步动作，执行后重新读取；失败有明确停止或换动作规则。
3. 首版策略覆盖基础经济、合理购买和升星、人口上限、前后排、合法装备，以及所有可能出现的选择节点。
4. 使用显式、可复现的机器人随机流，不使用 Math.random 决定领域行为。
5. 每轮限制操作步数，防止反复刷新或失败循环占满服务器。
6. 补位机器人在开局加入；临时接管机器人接手断线玩家现有资产，不新建另一份 Match。
7. 重连接管交接由房间排队处理，保证任何时刻一个席位只有一个控制者。

**验收标准**

- [ ] 1 真人加 7 机器人可从开场完成到最终排名。
- [ ] 全 8 机器人可运行不同种子的整局，用于自动化验证。
- [ ] 刷新后按新商店买卡，购买后新棋子可参与部署；合成后按新装备实例进行装备。
- [ ] 升级、升星、备战区满、装备冲突和金币不足不会造成死循环或非法写入。
- [ ] 强化、异常目标、掉落选择和超时兜底均可完成，不只会买卡和站位。
- [ ] 相同初始条件和命令顺序可复现机器人行为。
- [ ] 断线接管保留原席位、资产和历史；本人重连后不会与机器人同时操作。
- [ ] 机器人较弱可以作为质量残余，但无法完成对局属于未通过。

**证据与回退**

先验证“合法、能打完整局”，再调强度。若某策略失败，退回更简单的合法策略，不增加额外资源使机器人作弊过关。

### N6 正式游戏界面接入

**实施内容**

1. 新增远程 Session 适配器，让在线操作只发意图，UI 从可见状态更新。
2. 增加房间入口、八席列表、真人与机器人标识、准备和开始操作。
3. 接入当前玩家商店、站位、装备、选择、公开阵容查看和最终排名。
4. 服务器权威计算与浏览器播放分离：客户端播放当前战斗，不以本地推演写回结果。
5. 显示待确认、拒绝、断线恢复、自动接管和房间异常结束状态。
6. 保留界面已有的必要只读依赖；在线路径不再调用本地权威 stepMatch。
7. 处理事件监听清理、重复进入房间、初始玩家列表、资源子路径与版本不兼容提示。

**验收标准**

- [ ] 两名真人加六机器人、单人加七机器人都能用正式界面完成一局。
- [ ] 创建者和加入者进入房间立即看到完整玩家列表；房主开始及机器人补位清晰可见。
- [ ] 每人只操作自己的资产，查看对手不会把对手状态覆盖成本人状态。
- [ ] 双方画面使用同一权威 battleId 与结果，角色、位置和血量映射正确。
- [ ] 战斗初始事件、结束事件和结算显示完整；快进或省略部分动画不丢权威事件。
- [ ] 浏览器后台后返回、刷新重连、重复退出进入均正常；旧监听不重复发送命令。
- [ ] 服务器拒绝时 UI 恢复正确显示，不残留“已购买”或“已准备”的假状态。
- [ ] 淘汰玩家只能执行允许的观战行为，仍能看到最终排名。
- [ ] 在线局不能被本地存档导入、离线新局或回放按钮覆盖。

**证据与回退**

记录两个实际浏览器的操作和同一房间事件。发现 UI 与状态合同不匹配时修适配器或明确修订投影，不把服务器内部字段整包公开给 UI。

### N7 目标服务器验收

**实施内容**

1. 固定候选版本，在目标 4 核 8G 环境部署测试服务；明确测试地址、进程和停止方式。
2. 明确静态前端与对局服务的交付方式，使用 HTTPS 与 WSS，核对代理、子路径和版本兼容。
3. 测量一个八席房间的准备操作、四场 PvP、最多八场 PvE、机器人和事件发送。
4. 在至少两台实际电脑上联机试玩，其中至少一个客户端走不同网络。
5. 按第 8 节完成自动化、网络故障和用户体验验收。
6. 保存候选版本、测试结果、性能残余、回退版本和实际启动停止步骤。

**验收标准**

- [ ] 1 真人加 7 机器人和至少 2 真人加其余机器人分别完成完整真实对局。
- [ ] 八个独立测试连接能同时在线；不要求为了验收邀请八名真人。
- [ ] 满负载战斗期间仍能响应连接、重连和必要控制消息，不被长同步循环饿死。
- [ ] 断网、重连、进程结束和计算任务失败均呈现合同规定的结果。
- [ ] 实测性能达到 N0 至 N2 阶段确定的目标；历史 M8 CPU 失败没有被藏入新报告。
- [ ] 用户在固定候选上试玩，确认“能和朋友完成八人局”的实际体验。
- [ ] 未解决问题列明对使用的影响；不以没有任何改进空间作为完成条件。
- [ ] 发布说明明确当前容量是一房间已验证，不推断未测的并发房间数。

**发布与回退**

开发和测试证据不自动授权替换正式站点。正式合并与部署依据届时用户指令执行；有授权则继续，不重复索取同一授权。回退采用上一个固定构建及停止新开局，不承诺把进行中的新协议对局恢复到旧版本。

### 8.2 性能目标

原有固定 50 ms 逻辑步长保持不变。已有 M8 领域 tick p95 不高于 5 ms、p99 不高于 10 ms 的目标及历史负载保留；不把 Node 新构建结果直接冒充旧采样的通过结论。

以下是首版新增服务指标的建议预算，在 N0 至 N2 根据基线测量定稿。它们不是现已达成的成绩，也不能代替现有 M8 验收。

| 测量项 | 建议目标或判定办法 | 条件 |
| --- | --- | --- |
| 本机命令确认 | p95 不高于 100 ms，p99 不高于 250 ms | 八席在线，记录样本数与是否处在战斗计算阶段 |
| 服务端命令排队与处理 | p95 不高于 50 ms，p99 不高于 100 ms | 不含公网往返，用于区分服务器与网络问题 |
| 重连恢复 | 服务可达后 5 秒内恢复当前可见状态 | 不含用户网络本身不可达的时段 |
| 战斗计算 | 四场 PvP 和八场 PvE分别测总时长、队列和 CPU；N2 后再制定可兑现预算 | 不在未测前承诺单战 5 秒或四战 10 秒 |
| 战斗播放 | 开战等待和结算等待有明确上限；以固定候选真人试玩定稿 | 若一次算完再下发造成明显等待，改用分批结果或快照播放 |
| 内存与生命周期 | 记录高水位；连续房间结束后资源能释放，不持续单向增长 | 先预热，再重复完整生命周期；原 H1 残余独立注明 |
| 浏览器表现 | 沿用适用的桌面帧率及资源预算，并单独验证在线界面 | 服务器 CPU 通过不能代替浏览器硬件验证 |

CPU 密集战斗不能仅靠 async 或 Promise.all 实现多核计算。优先采用可测的有界调度；若单线程批次无法满足网络响应，隔离到工作线程池。池大小依据测量确定，要给网络、房间提交和系统留余量，不以“四核就四个长期满载计算线程”为固定规则。

实际公网命令往返须分开报告网络延迟与服务器耗时。没有网络条件说明的“低于 100 ms”没有可比性。

原性能目标未满足时，可以继续独立的功能验证，但不能声明正式性能验收通过。若用户决定修订发布预算，必须保留原结果、修订理由和新标准，不把旧失败改名为成功。

### 8.3 每阶段的最小证据

每次交付记录：源码版本、已实现行为、测试命令与结果、关键独立预期、已知问题、下一阶段入口。截图用于证明界面和交互，不能替代领域结算断言；相同算法在两处得到相同结果也不能替代独立数值预期。

不要求每阶段重跑所有历史对局。按改动影响选择检查；规则或公共契约变化时补相应领域回归，正式候选再执行适用的完整检查。测试名称和命令在新增脚本后才写为可执行入口，不能照抄不存在的脚本并声称验收通过。

### 9.4 失败处理

- 同一失败重复出现且没有新增证据时，停止原样重试，缩小到可以区分原因的输入或阶段。
- 保留已经通过的模块，修正受影响的接口，不因为一个局部错误推倒全部架构。
- 房间发生不可恢复异常时明确中断，保留可定位记录；不悄悄跳过结算、吞掉事件或以机器人作弊补偿。
- 仅玩法取舍或授权变化需要用户决定。普通编译错误、构建配置和实现缺陷由执行者在已授权范围内修正。
- 不执行强推覆盖 main、删除旧规则、覆盖原证据或清空玩家状态来让验收表变绿。

## 11 首版完成判定

只有下列条件全部满足，才可称“八人联机首版完成”：

- [ ] 真人可从不同电脑进入同一私密房间，开局补满八个席位。
- [ ] 服务器唯一决定资产、随机数、战斗、结算和排名。
- [ ] 真人和机器人使用同一个有限卡池，购买、刷新、升星、出售和淘汰满足库存守恒。
- [ ] 双方真实阵容及效果参与同一战斗，每对阵只有一份权威结果，结算只提交一次。
- [ ] 开场、PvE、PvP、选择、补给和终局按定稿合同走完。
- [ ] 基础机器人可完整参赛，人数不足与断线接管均按规则运行。
- [ ] 玩家短暂断线能回到原席位，旧连接与重复请求不会破坏状态。
- [ ] 正式界面可操作、可看战斗、可查看公开阵容和最终排名。
- [ ] 目标服务器的一房间负载、网络故障用例和真人试玩均通过。
- [ ] 未达成的可选增强和已知质量残余明确列出，没有冒充已完成。

“可以创建房间”“八个连接连上了”“机器人在买卡”或“两个浏览器看到相同 JSON”都只是阶段成果，不能单独替代以上终局验收。
