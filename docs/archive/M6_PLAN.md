二、M6 目标

让玩家能够：
1. 开始一个新随机局，也能输入种子复现同一局。
2. 关闭页面后，从最近一次成功保存的合法状态继续。
3. 在准备、结算或终局查看已完成战斗，理解伤害、护盾、治疗和目标变化。
4. 在桌面和手机上清楚看到棋盘、商店、关键属性和操作结果。

这轮完成一条完整的用户路径：
启动 → 新局或继续 → 运营与选择 → 战斗 → 自动保存 → 刷新继续 → 战斗结束 → 查看回放与统计 → 返回当前局 → 完成对局 → 新局。

规划依据：当前 MatchSession 的 New Match 重用原 seed，账本只保留当前战斗且换轮清空；公开 serialize/restore 已存在，但没有玩家存档导入界面；页面仍以 960×800 的 Phaser FIT 画布和 DOM 策略栏组成。M6 在这些已验证边界上补产品能力，不重写对局规则。

四、必须冻结的产品与数据合同

4.1 种子与新局身份

随机新局的 uint32 seed 在领域外、用户真正创建新局时产生一次，并显式传给 createMatch(seed)。已有商店/选择/奖励/战斗 RNG 不参与 seed 生成。不得把时间或非确定性随机源放入 Match/Combat 推进。

固定 seed 接受完整的 0 至 4294967295 整数，含 0；空值、负数、小数、NaN、截断字符串和超界值有明确提示且不改变当前局。相同 seed 与相同命令保持完整状态和事件可复现。

runId 标识一局，与 seed 分离；同 seed 重开也产生新 runId。存储 revision 与 activationEpoch 仅服务持久化，不进入规则和内容哈希。

启动轻量入口显示“继续对局”和“开始新局”。当前未完成局被新局替换时，产品界面明确说明会替换当前自动存档，并保留导出当前局入口；不做多槽管理。

4.2 自动保存与恢复粒度

采用 IndexedDB 的一个当前槽及最近三个完成局档案。当前局和不可变历史战斗分开存储，避免每 40 ticks 复制整份历史。

接受且确实改变状态的命令、阶段转换、战斗开始/结束及新局创建后排队保存一致快照；战斗推进路径每 40 个逻辑 ticks 排队保存一次。M5 的一个 tick 为 50ms，因此正常保存调度间隔为 2 秒模拟时间。恢复点是最近一次事务成功提交的合法 tick，未提交写入也可能丢失；不能承诺任何关闭情况下都绝不丢 2 秒。

保存必须覆盖 MatchSession.advance() 的战斗推进与结算，不能只钩住用户命令 commit()。帧时间累计器、DOM、Phaser 对象、动画和音效状态不入存档。

后台切换时暂停活动对局并尝试保存；重新显示页面不按离开时长追赶模拟。页面突然关闭不依赖最后一次异步卸载写入保证数据。

快照在排队时固定，带事件游标；写入事务内检查 runId、activationEpoch 与预期 revision。乱序回调及旧局写入不能改写新局 current 指针。导入相同 runId 的旧文件也必须获得新的本地激活代号。

同一个槽只允许一个有效写入序列。检测到另一标签页或另一激活代号已修改槽时，当前标签停止自动写并提示冲突，仍允许本地导出；不实现跨标签合并。检查必须在事务内，不能只在回调中比较内存变量。

UI 状态至少区分“保存中”“最近保存成功”“保存失败”；仅在事务完成后显示成功。配额不足、事务 abort 或冲突不破坏正在玩的局和最后有效存档。

完成局归档和保留上限维护放在事务中。第四个完成局提交成功后才淘汰最旧完成局；不能先删旧档再尝试写新档。

4.3 存档包装与导入事务

外层独立版本化：文件 kind、saveFormatVersion、replayFormatVersion、runId、当前 Match、该局战斗档案及必要元数据。保留内层 schema、rules/content/protocol/RNG 版本和 digest。显示版本信息供定位问题，不把技术字段常驻主要玩法界面。

本轮默认只支持本轮正式导出的包装格式。拒绝未知版本、旧 digest、裸 M5 MatchState 和损坏历史；不承诺迁移旧开发存档。M5 的结构校验不是命令历史的密码学证明，M6 不把内容摘要宣传成防作弊签名。

导入顺序固定：
解析文件 → 验证外层边界 → restoreMatch 验证当前状态 → 在冻结的历史上下文中验证战斗档案 → 构建候选会话 → 持久化事务成功 → 替换活动会话与 UI。

导入期间暂停领域推进与输入，避免旧局继续变化造成竞争；失败后恢复原会话，时间累计器不能补算等待时长。解析、验证、档案缺段、配额或事务任一失败，均保留旧 Match、RNG、账本、收据与最后有效存档，不能先 reset 再校验。

导出从同一个合法 tick 捕获 Match 与档案游标，无需先写入存储；即使自动保存失败仍能导出。导出与回放都不消耗领域 RNG。

MAX_SAVE_BYTES、MAX_BATTLE_RECORDS、单战事件上限、导入校验耗时和文件体积上限在接口冻结阶段依据合法最大负载实测确定，写进常量和验收表。不能使用未经测量的低阈值拒绝合法完整局，也不能完全不设解析边界。

4.4 战斗档案与历史正确性

战斗身份采用 (runId, combatId)；当前 combatId 类似 round-N，单独使用会跨局冲突。

每份 BattleRecord 必须保留：
a. 足以验证当时阵容、星级、装备、羁绊、强化、异常、成长及随机态的冻结开战上下文。
b. 完整 tick 0 事件与开战状态。
c. 从 tick 0 起至记录终点的完整、连续、有序事件。
d. 已录到的 tick、事件序号、战斗结果及状态/事件校验值。

默认以不含档案自身的战前 Match 快照作为开战上下文，复用现有验证能力；若改为紧凑上下文，必须证明信息等价并在 F1 冻结验证协议。历史英雄已被出售或升级时，仍按当时阵容验证，不能拿当前 Match 阵容校验过去 Combat。

当前战斗的 Match 快照、事件前缀与记录终点必须同一 tick 对齐。自动保存只保存合法边界，不允许半个 stepMatch 事务。

Continue/New Match 清空当前账本前完成归档；tick 0 钩子、成长和战斗结束事件各一次。补给轮没有战斗，不伪造 BattleRecord；可显示其既有结算信息。常规完整局包含 35 轮，其中 30 场战斗。

只读 PlaybackSession 在隔离副本重演。事件流不是完整状态替代物，因为它不单独编码所有冷却、任务和 RNG；应从冻结上下文或经验证的检查点推进，并核对事件。

回放检查点是稀疏、可丢弃缓存，可按需生成；不每 tick 持久化完整状态。检查点必须与 tick、nextEventSeq 和事件前缀对应。Seek 从最近合法检查点恢复；向前、向后和倍速变化不会重复事件或漏算状态。

回放 2×/4× 表示单位显示时间内推进更多个固定 50ms 逻辑 ticks，不改变每 tick 数值规则。暂停不推进。回放不得调用活动 Match 的结算、命令或存储路径；返回后活动 Match 与存档 revision 不变。

死亡单位 AP 仍使用 M5 允许的有限停止值。完整档案可以结合死亡事件与重演验证其真实来源，但不应强迫死亡单位继续增长到当前 tick 的 AP。无需单为这一点升级 schema5。

4.5 战斗统计口径

伤害输出：按来源单位累加 packetDamage.hpDamage，物理/魔法分项可在详情显示。
护盾吸收：按受击单位累加 packetDamage.absorbed。
有效治疗：按来源单位累加 heal.actual；若显示过量治疗，单列 heal.overheal。

不能同时累计 packetDamage 和汇总 damage，不能把盾生成量当实际吸收量。洛里斯分担包保持原伤害来源、实际受击目标，转移伤害只计一次。本轮不增加按护盾提供者分账的复杂支持统计。

独立例子：
475 分担为 238/237；若目标盾为 100、洛里斯盾为 200，实际 HP 伤害为 138+37=175，吸收为 300。
请求治疗 100、实际缺血 30，则有效治疗 30、过量 70。
同 tick 多段伤害、过量伤害、多个护盾、目标死亡和分担均有手写预期。

展示可以合并同 tick 飘字、限流装饰或缩短显示历史，但不得删除权威事件或用另一套伤害公式。选中单位详情优先显示名字、星级、生命、法力、物理/魔法来源、当前效果；内部 ID 放调试详情。

4.6 响应式与交互

保留 Phaser 棋盘与 DOM 面板分层。把棋盘、商店、HUD 和主操作重新分区，避免将完整 960×800 面板整体缩到手机屏幕。

验收视口：1440×1000、1440×600、390×844、844×390、360×640。允许详情纵向滚动和折叠，主操作可达，无横向溢出。横竖屏切换后布局与输入坐标一致。

主要 DOM 操作目标宽高均至少 44 CSS px。原型阶段冻结棋子实际可见直径目标，建议至少 32 CSS px；若直接触摸目标不足以稳定操作，必须提供清楚可用的 DOM 选中/部署路径。CSS 实际 bounds 与截图验收，不能用画布逻辑像素冒充。

D/F/锁店、开始/继续/新局保留一个清楚的主操作区；策略、存档、回放、统计作为独立组件挂载，避免每条工作线改同一个大文件。

玩家可见属性、状态和失败原因使用中文；展示全队与成员收益、明确最后一排、过量与实际数值。错误提示由领域 reason 映射，不在 UI 重新判定经济规则。

M4 触摸单次提交、触摸后鼠标重复过滤、取消/正常松手配对、选择弹窗遮挡、键盘 repeat、快速 D/F/E、旋转和重开清理继续有效。

七、验收清单

G01 种子：
0、42、4294967295 合法；非法输入不变更当前局。随机新局显示的 seed 可通过固定 seed 重现完整状态/事件，新局身份不同。

G02 恢复阶段：
覆盖初始组件选择、强化、异常目标/offer、准备、进行中战斗、盾/持续状态/引导与任务、结算奖励和终局。
覆盖 tick 39/40/41、战斗开始/结束、Continue。恢复不重复 tick 0、收入、奖励、异常收据或成长。

G03 历史完整性：
正常两战后进入第三战，刷新及文件往返后，第三战恢复到最近成功保存点；完成第三战并进入允许阶段后，前两战可从 tick 0 完整回放。出售过渡英雄后，历史仍显示原英雄/装备/成长。

G04 原子性与竞争：
坏 JSON、错外层版本/schema/digest、非法运行时字段、缺失事件段、错检查点、超限文件均拒绝。
模拟事务 abort、配额不足、乱序写入、新局覆盖、同 runId 旧文件重新激活、第二标签写入冲突。
失败时活动状态、RNG、收据、账本与最后有效档保留；旧任务不能赢过新激活代号。

G05 回放一致与隔离：
四条路线各场的重演状态和完整事件与原战斗对应；起始、中间与终局严格一致。只读模式下 D/F/E、部署和购买不能改变真实局。
暂停、seek、换速和返回不改变真实 Match、四条 RNG、金币、ID、收据、事件序号与存储 revision；不重复增长或结算。

G06 数字准确：
手写盾/分担/过量伤害/治疗预期，浏览器数字与同一战斗账本一致。
保留 M5 475→238/237、羁绊 20/50 和 36/75、最后一排、异常候选回返、空阵容恢复与死亡 AP 停止增长回归。
生产聚合器不能兼作唯一预期 oracle。

G07 真输入与布局：
五视口检查实际 CSS bounds、可读性、横竖屏转换及主操作可达。
保留全部 M4 触摸和快速键盘语义，验证导入/回放层遮挡和焦点。
没有未解释 console errors。统计、存档与回放页面不能劫持棋盘输入。

G08 生命周期与容量：
重复新局、导入、回放进入/退出后不累积监听器、tween、计时器或旧账本；每次只存在一个活动领域推进器。
第四完成局安全淘汰；最大合法存档可往返，存储失败可导出；不保存每 tick 完整状态，不重复拷贝全部历史。

G09 门禁：
已有 643 项所在的有效语义必须保留；新增后数量可增加，不以固定测试数代替覆盖。
规则未变时旧领域轨迹不应无解释改变；若公共包装导致测试调整，保留历史预期并说明修改原因。
全套 typecheck/build/领域/恢复/原生输入/正常浏览器路线均在最终同一提交通过。
