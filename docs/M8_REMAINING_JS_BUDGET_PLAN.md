# B7 合并后：M8 剩余批次与中文名称接入的 JS gzip 预算建议

日期：2026-10-09 UTC。性质：**只读诊断、规划估算，等待用户决定，不是门禁变更或未来实现验收**。

## 结论

建议请求用户批准：保持“全部生产 JS 文件各自 gzip level 9 后求和”的口径，将相对签收 M7 的 JS 倍数从 **1.15 调整至 1.30**。以本次同工具链重建 M7 的 **424,763 B** 为锚，整数有效上限为 **552,191 B**，约 **539.25 KiB**；不是 552,191 KiB，也不是在当前 B7 上再乘 1.30。

固定 B7 合并树 `87782695f864ba5d493d7a40c9c3652b48aacc86` 实测 **485,743 B**。六项剩余工作的净增加规划低/中/高情景分别 **18,000 / 32,000 / 51,500 B**，最终总量 **503,743 / 517,743 / 537,243 B**。建议上限因此在高情景之上保留 **14,948 B**，用于 B10 集成修正、已登记 U4 消费端收口、打包交互和尚未确定的名称范围；它不是任一批次可以无理由用满的配额。

当前上限 **488,477 B**，只有 **2,734 B** 余量。仅令 U5 的既有公共查询进入生产包就实测增加 **1,657 B**，留下 **1,077 B**；完整 U5 界面还没计入。因此“沿用现门槛直至所有剩余批次完成”不是可信规划。**本次没有修改门禁、CI、产品源码，也没有执行未来批次。**

## 1. 测量边界与可复现性

- 所有本次实测以独立 `git archive <fixed SHA>` 副本构建，未修改正在工作的产品 checkout。探针仅在 `/tmp` 隔离副本增加一个独立诊断入口，并由该副本的 HTML 引入，未编辑任何产品 UI 文件。
- Node **v22.23.3**，zlib **1.3.1-e00f703**；共享既有依赖，不安装/升级。lockfile SHA-256：`3f10c2dd761075fc3806aa2ef1459d036ac1068d9a15ab3356f3f1fffe42379f`。工具版本详见 evidence/m8-bundle-planning/tool-versions.json。
- 每次执行完整 `npm run build`（含 TypeScript 检查及 Vite production build），按 [`scripts/m7-budget.cjs`](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/scripts/m7-budget.cjs) 的 `jsGzip` 规则，枚举全部 `dist/assets/*.js`，逐文件 `zlib.gzipSync(data,{level:9})` 再求和。本次各树均为一个 JS 文件；不是只测入口，也不是采用 Vite 显示的 gzip 数。
- CSS、图片和离线档案不计入现有 JS 门禁；本方案不靠把必要运行数据移到其它资源类型规避预算。以后拆 chunk 仍计算全部 JS，且多个 gzip 字典可能增加总和。
- 测量脚本、原始 build 输出、每个产物 raw/gzip 字节和 SHA-256 已随报告保存在 `evidence/m8-bundle-planning/`；不提交 dist/node_modules 或临时副本。
- 未来批次没有实现，以下整数是规划刻度，不是预测精度、保证上限、置信区间或未来实测。gzip 上下文/符号压缩会变化，不能按源码行数或 raw 字节固定比例外推。

### B8/B9 的可审查拆分（规划，不是假想构建结果）

B8 6/10/16 KB 可进一步理解为：有限表/池与计划 **1/1.5/2 KB**；授予/资格/自选/容量/终局原子状态机 **3/5/8 KB**；本批恢复/谱系/查询/校验 **2/3.5/6 KB**。这比“野怪掉落仅多一张表”更符合批准的工作范围。既有永久物品授予规划器和八组件映射已经在基线中，不再购买一遍。

B9 5/9/15 KB 为：旧档识别/保全/导出/隔离 **1.5/3/5 KB**；整局验证和33战存储/回放集成 **2/3.5/6 KB**；正式事件和兼容查询/应用路由 **1.5/2.5/4 KB**。协议字面量变化本身很小，预算主要来自执行/验证分支。若需要额外旧引擎、多语言框架或通用 schema 库，就已经超出此假设，不能直接吃掉预留后声称估算准确。

## 4. U5 探针解释及避免重复计算

[`encounter-selectors.ts`](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/src/simulation/encounter-selectors.ts) 现在有19英雄的简明规则文本、中立机制说明及投影逻辑，但没有生产消费者，所以这些专用文本/查询逻辑尚未进入基线包。探针将它及 `readRoundInfo` 放入可观察的 globalThis 属性，阻止 tree shaking；无需调用/伪造游戏态即可测量首次可达的成本。

**1,657 B是该精确诊断入口的净增量**，包括少量保留绑定开销与整包压缩变化；不是最终U5的严格理论下界。未来消费方式或同时引入其它代码会改变压缩。该费用归U5，不归B7补记，也不再向B8或U7收费。其后端目录/快照等已经可达的依赖不重新打包计算。

B8 的奖励权威查询第一次接线费用全部归B8；U6仅估消费端。B9的兼容性/回放算法与公共查询全部归B9；U7仅估UI。B8新增账本的局部恢复归B8，B9只算整局跨模块校验和版本集成。B7已有12中立定义、25实例、8遭遇及其恢复成本已经包含在485,743B，不再列为未来预算。

## 5. 中文名称：当前44项、广范围89项与说明严格分开

明确的B1外遗留清单为 **44装备名称核对**，来源：[中文跟进](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/docs/M8_LOCALIZATION_FOLLOWUP.md)、[名称审核表](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/docs/M8_ITEM_NAMES_REVIEW.md)。现已有中文名；[UR-U3-04](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/docs/UI_REQUESTS.md) 明说状态改为verified后现UI暂译标记会自动消失，不需要为此重新实现一套界面。

同时，[hero-identity.ts](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/src/presentation/hero-identity.ts) 已有 **17个羁绊中文标签**，其中5个开放职业，其余是表现用原生羁绊，保留客户端字符串表逐字核对的遗留说明。[M7交接](https://github.com/catfish-xn/cat/blob/87782695f864ba5d493d7a40c9c3652b48aacc86/docs/M7_HANDOFF.md) 也记录该点。因此没有把用户“M8后中文译名接入”擅自缩成仅44项。

本次广范围探针为 **44装备+19英雄+17羁绊+6强化+3异常=89条**，覆盖当前公开内容目录的名称类别；5个开放职业已包含在17个羁绊中，不能再加一次。这里的名称都是当前运行/表现层已有文本，不是新取得或已核验的官方中文。

- **原位替换**：小范围名字更正与状态修改可以接近0增量，也可能略减；不能预先承诺节省。真实译名与客户端原档尚未取得/比对，不能精确预测差值。
- **额外最小表**：44条按apiName→name增加，实测+1,039B；89条按现有稳定键增表，实测+1,684B。它刻意保留旧名再加表，是保守的附加结构诊断，不主张最终保留重复译名。对应字典原件已保存，未加长说明、effects、图标、其它模式条目或来源逐项长文本。
- **预算取法**：如果最终只44项、直接替换，低/中/高可以按0/500/1,500B单独看；总表采用更广的0/1,500/3,000B，为范围未完全确定留空间。89条以外12个项目中立模板名可纳入3KB高档的小范围预留，但它们是项目定义，不能强行声称有官方逐项中文映射。
- **全量说明另议**：英雄技能/装备机制说明不是“名称”。当前已有核准的装备中文效果和项目规则说明，导入客户端完整desc会带入占位符、富文本、未实现机制或数值冲突，需另行限定条数、生成策略、运行字段与预算；本次没有给任意长度全文翻译开绿灯。
- **完整原始 zh_cn.json 不进生产依赖图**：原件只作为离线审计输入，保存hash/版本，离线提取需要的稳定键→名字，运行时只保留最小已用结果。来源档案大小不能当成运行JS增量，也不能把12MB英文原档大小套用到中文。此前原件路径字符串被digest保留不等于整个原文件已入包。

## 6. 新上限、备选方案与决策边界

| 方案 | 倍数 | 本次M7基线下有效整数上限 B | 相对当前B7余量 B | 高情景后的余量 B |
| --- | ---: | ---: | ---: | ---: |
| 维持现状 | 1.15 | 488,477 | 2,734 | −48,766 |
| 紧预算 | 1.25 | 530,953 | 45,210 | −6,290 |
| 较紧折中 | 1.28 | 543,696 | 57,953 | 6,453 |
| **建议** | **1.30** | **552,191** | **66,448** | **14,948** |

建议理由：1.25可容纳中情景，但高情景会超；1.28约6.5KB的高情景剩余较薄，相当于约一至两个既有UI批次增量，难覆盖B10/U4欠项与跨批恢复适配；1.30给高情景约15KB、中央情景34,448B空间，仍保持可追踪的全量门禁。它相对现有整数上限增加63,714B，相对当前B7允许约13.68%的后续增长；不能把“从1.15到1.30”误读为当前包允许增长30%。

**因素型与绝对值必须明确二选一**：本建议延续现有相对签收M7的factor门禁，只改factor的审批目标，552,191B是本次基线下的解释值。若用户希望跨工具链都固定552,191B硬上限，那是不同门禁政策，需要单独明确批准，不能在实施时默默切换。当前1.15数学值488,477.45B和1.30数学值552,191.9B都按整数产物取floor。

批准也只涉及JS总量：首交互1.20倍、保存/回放容量、性能、完整账本、恢复真实性及原有其它门禁不随之放宽。不预授权M9新增英雄、更多语言、整套UI库或框架；这些不在当前估算中。

## 7. 后续采用方式（待批准后执行）

1. 用户决定是否采用1.30；目前只交本报告，不改任何阈值。
2. 每个批次在最终固定整合SHA重新build、逐JS gzip9求和；记录该批前后SHA、工具链、总量、净增量与原因。不拿独立分支raw-head差值当合并后的净新增。
3. U5特别核验本次1,657B首次可达成本；B8交付后重新估B9，因为账本/序列化边界将真实可见；B9/U7和中文合入后，再由B10验证最终总量和所有其它原门禁。
4. 批次超出本表高档时先报告原因并更新预测，即使总门禁仍过也不默默消耗全部预留。不承诺用未经授权的删元数据、改digest、移除调试支持或跳过验证来填洞。
