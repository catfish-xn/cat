# H1 堆门禁诊断收尾报告

## 结论

**运行/测量波动与真实保留增长并存；没有证实可复现的持续业务对象泄漏。** 不能把所有超限都归为纯噪声，也不能把端点差值超限直接判成业务泄漏。

- 无快照preview三条连续轨迹后3窗净增分别+438,252、−11,744、−301,400 B，没有一致可复现的后段上涨；其中一条先增1,029,924 B、下一窗回落960,984 B。dev单轨迹末3窗+415,784 B，但中途−944,020 B，终点低于第1/2窗。波动明确；有限窗口不能排除慢/晚发泄漏。
- 同会话七份快照中，ResourceTiming数量36→171，DevTools ResourceData 61→196，逐窗仍累积，有真实保留链。编译代码也增加。故不是“所有变化都没有真实对象增长”；这些增长不自动等于无界业务泄漏。
- 快照组受采集扰动，不能给无快照每次失败逐一归因。真实增长、缓存/编译、工具记录、运行状态各占多少，现有数据不能定量拆分。

本报告为诊断交付，不是修复实施、无泄漏保证或开发者自签。最终签收由独立Pro审计给出；门禁修复方案由用户决定。

## 为什么现行两端点规则不稳

同SHA的post-GC起点并不相同；preview起点范围13,950,140–15,658,700 B，终点14,375,840–16,154,504 B。高终点可因起点高而通过，较低终点可因起点低而失败。两端点差不能区分启动/编译阶段、暂时波动和持续保留。跨CPU/job存在混杂，不声称起点是唯一原因。

普通CI112同a3ea85c5首轮preview增1,662,412 B失败，一次获准重跑后增−219,360 B通过；[首轮与重跑证据](evidence/h1-ci112/README.md)均保留。重跑实际覆盖compare依赖的完整作业集合。没有修改门禁，没有把首轮失败抹掉，也没有将这组混入预登记正常12次。

## 门禁修复方案及误报/漏报估算

详见[修复提案与条件回放](H1_GATE_PROPOSAL.md)。建议后续修复任务先影子验证**3个新进程×6个等长窗口，保持阈值，三态判定**：

- 每进程D=H1−H0、G=后3个边界中位数−前3个边界中位数、T=H6−H3、K=最大单窗增量；任一严格>L记hit。
- 3进程≥2 hit阻断，1 hit待复核且不能自动放行，0 hit只通过当前观察窗。缺失/超时/身份错不通过。不能用重复择优重跑替代复核。
- 六窗每进程实测约30分钟，三进程约90分钟计算量/模式；双模式约180分钟计算量，并行可缩短墙钟但不减少资源成本。是否承担这一成本由用户决定。

现有数据可估出的范围：

- 原12次启动分支按job三次回放：4组中0硬阻断、3待复核、1无异常；完整三条六窗只有1个组合，0hit。这是历史决策回放，**没有独立真阴性标签，不能说真实误报为0%**。
- 若强假定原25%全是独立噪声，三次多数启动分支硬拒绝概率15.625%、单hit复核42.1875%；不是实测FPR，不适用于整个六窗规则。
- 在现有preview三轨迹上固定5形状×7个正幅度数学叠加：DGTK为19阻断、5复核、11放行。64KiB/窗线性仅复核，128KiB/窗在该背景下阻断；晚发/慢增长仍可漏过。**11/35不是实际漏报率**，没有概率权重和GC反馈；详列每种形状/幅度而非虚构精确FNR。
- dev只有1条完整轨迹，D/G/T/K均低于1.5MiB；脚本返回“三进程样本不足”，不伪造多数验证或借用preview误报率。

DG简化法会漏第6窗永久阶跃，DGT仍会漏第2窗永久阶跃，K补突增但增加噪声复核负担。三个候选的权衡、全部40数学场景及可复现脚本已提交。实际FPR/FNR仍不可识别；本任务按用户限定不追加真值实验，后续是否验证/实施由用户决定。
