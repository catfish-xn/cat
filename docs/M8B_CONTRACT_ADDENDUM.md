## 1. 继承的合同与实际缺项

以下要求继续按 [M8_RULES.md §8–10](M8_RULES.md) 执行：

- 首次进入本轮准备期，在同一领域事务中冻结遭遇和完整掉落计划；已有计划必须复用。
- 揭示资格只采用 `source-killed` 或已批准政策的 `approved-guarantee`。部分击杀、平局、失败不抹除已获得的资格；未满足资格的计划在战斗结束时成为 `forfeited`。本轮不增加漏掉奖励顺延。
- 掉落身份继续使用 `[roundId, encounterId, sourceUnitId, slotOrdinal]` 的 canonical tuple；授予收据身份继续为 `[dropId, "grant"]`。
- 实际资源与唯一 `LootReceipt` 原子提交；未授予不计已领取或保底。所有金额、计数、序号为安全整数，50 ms/tick，显式 RNG。
- 数量大于 1 的英雄奖励拆成独立的数量 1 条目。满席英雄进入 `pending-capacity`；终局仍不能入库的英雄进入 `retained-terminal`，无收据、不计保底、不换金币、无操作，不阻止 `gameOver`。
- 完成战斗时保留“掉落揭示／授予 → 经济与成长收据 → 终局判定”的一次提交顺序。重复 step、Continue、旧选择命令、恢复和回放不得再发一次。
- `gameOver` 拒绝运营；D2-A 的旧档只读保全和 M8 版本切换方式不变。

冻结接口与本次需求之间存在以下缺项，不能以数据填空或特殊物品名绕过：

| 需求 | 当前边界 | 本文提议的最小增补 |
| --- | --- | --- |
| 击杀后选择一个组件，并保留掉落来源与保底收据 | `LootPayload` 仅为具体 gold/item/unit；`DropState` 在 planned 时已有具体 payload | 独立组件选择描述、资格账本与解决记录；确认后生成现有形状的具体 item `LootReceipt` |
| 用原选择命令处理新掉落选择 | 当前 `selectChoice` 对 component 发 `ScheduleReceipt`，当前恢复器要求选择存在于旧日程 | 依据权威选择来源派发；保留公开载荷，新增领域分支与恢复验证 |
| 中立同伴死亡回血／加攻速 | G06/G01 能执行结果，但 G09 `Trigger` 没有单位死亡事件 | 有限死亡批次输入、冻结的同伴范围与一次消费身份 |
| 狼开场跳后排、先锋开场冲锋 | G10 可以选目标；`Effect` 和 `AbilityOperation` 没有位移操作 | 有限、仅开场一次的重定位／冻结路径计划，以及分开的位移与后续伤害消费记录 |
| 龙的方向性溅射 | 现有路径和主目标邻域不等于声明的四格锥形 | 增加 ENCOUNTERS 指定的有限四格几何选择器，最多 2 个次要目标 |
| 鸟的攻速实际生效 | 当前中立攻击直接返回固定 `attackIntervalTicks` | 中立攻击调度消费 G01 的最终攻速；基础表示与舍入明确 |
| 新中立模板的基础暴击 | 基线中立默认概率为 0，单位目录／解析属性没有基础暴击输入，当前恢复器也只接受中立 0 概率 | 增补 B3/G03 基础输入通路；B7 从声明内容编译初始战斗投影，B9 按同版本内容验证；不改变技能暴击授权模型 |
| 新中立模板的零蓝输入 | G08 已有无蓝语义，但 `validateUnitDefinitions` 当前要求 `maxMana>=1` | 明确 B3/G08 输入边界，B7 导入／目录校验接受合法 `initialMana=maxMana=0`，B9 恢复相同约束 |
| 掉落英雄在成长回写前触发升星 | 原购买流程只迁移当时已存的成长，本战 delta 仍以 Combat 原单位 ID 标识 | 沿同次事务的 `unitUpgraded` 谱系同时迁移本战 delta，随后只回写一次 |

## 2. 组件自选的独立计划与账本

### 2.1 保持具体 LootPayload，不虚构库存物品

组件自选是“一个具备掉落资格的选择机会”，不是已经入库的组件，也不是锻造器、宝箱或可出售的消耗品。它不占装备库存、不参与合成、不获得永久物品 ID。

原 `EncounterPlan.drops` 仍只存具体 `DropState`，原 `LootPayload` 联合类型不承载 `component-choice`。新增的组件选择描述属于独立的 M8B 计划账本；未来类型集成可以使用明确命名的复合计划或扩展接口，不能直接把不兼容对象塞入原 `drops` 数组。

本文中“完整掉落计划”指 **原具体掉落计划＋本轮组件选择描述**。两部分必须在同一准备期事务完成冻结，统一遵守来源单位与槽位顺序，不得留到击杀、开奖或点击时补抽其中一部分。跨两部分的 `dropId` 不得重复。

以下为已批准设计的逻辑字段，不宣称这些 TypeScript 类型或运行字段已经存在：

| 独立选择描述中的信息 | 含义与约束 |
| --- | --- |
| `DropIdentity` 和槽位身份 | 复用 roundId、encounterId、sourceUnitId、dropId；槽位身份纳入原 canonical tuple |
| 描述类别 | 仅组件八选一；不是 `LootPayload.kind` 的新值，不扩展成任意奖励 N 选 M |
| `poolVersion` | 固定为 `m8b-components-v1`，引用 LOOT 中完整的 8 个合法组件及其 apiName 代码点排序；随内容 digest 冻结 |
| `terminalFallbackDefinitionId` | 从上述 8 项中等概率预抽的具体组件，必须属于该池；仅终局使用 |
| `revealCondition` | 仍只有 `source-killed`／`approved-guarantee`，所引用政策须可验证 |
| 数量 | 固定为 1；多个自选机会拆成多个独立槽位 |

固定 8 项的完整候选集合可以由冻结 `poolVersion` 引用，不必为每个槽位重复保存 8 个 ID；恢复时必须解析为该版本的精确集合，不能改用运行时“最新组件目录”。

### 2.2 资格与解决记录分离

选择描述本身不因玩家点击而修改。另有资格状态：`planned`、`revealed`、`forfeited`。其中 `revealed` 表示取得选择资格，不表示已经拥有组件。

一次解决记录至少关联 `dropId`、唯一 `receiptId` 和解决方式 `player-choice`／`terminal-fallback`。所选组件直接由对应 `LootReceipt.payload` 读取；若实现为便于查询再保存一份 definitionId，恢复必须校验两者完全一致，不能形成两个可各自修改的权威值。

状态含义为：

| 资格状态 | 解决记录 | 合法含义 |
| --- | --- | --- |
| planned | 无 | 尚未满足击杀／批准保底条件，UI 不展示隐藏计划 |
| revealed | 无 | 已取得资格，等待本轮战斗结束后选择或终局自动处理 |
| revealed | 有且对应实际收据 | 已解决并授予具体组件；不能再次选择 |
| forfeited | 无 | 本轮未赚得奖励；不会因终局备用项而复活 |

不接受 planned／forfeited 状态带授予收据，不接受同一 drop 多份解决记录。各轮选择描述和解决记录随本局保留，足以验证历史奖励；当前可操作的一项才投影成 `PendingChoice`。不靠 UI 私有队列保存选择进度。

### 2.3 RNG 与隐藏备用组件

候选固定为全部 8 项，不抽候选、不支持刷新，确认消费 0 个随机词。每个自选槽位在首次准备期从 **loot 流**均匀抽取一次备用组件，与直接掉落按同一来源单位／槽位顺序冻结。

采用 B2 拒绝采样：`n=8` 时全部 uint32 词均可接受，以 `word % 8` 选项，恰消费 1 词。该词即使最终被玩家正常自选替代也不退还、不挪给后续槽位。备用组件不能借用 shop、choice、reward、equipment 或 combat 流。

准备期预览和普通自选面板不公开未使用的备用组件；只有终局实际授予它时才显示真实奖励。读档、切页、查询、重复点击和非法命令不得重抽备用项。新增随机边界应纳入 M8 内容 digest 和逐词复演验证，不改变 B2 的流初始化。

### 2.4 实际授予只发一份 LootReceipt

正常选择或终局备用解决时，同一事务完成：验证资格和未解决状态 → 确定具体组件 → 分配 1 个永久 item ID → 放入库存 → 创建原形状的 item `LootReceipt` → 写入一次解决记录 → 更新按实际收据定义的计数。

此收据的 payload 为合法组件、quantity=1；`grantedItemIds` 恰为该次实际创建的 1 个 ID，`grantedUnitIds` 为空。领取时间可能晚于资格揭示时间，但 sourceUnitId、roundId、dropId 仍是原始来源。

同一自选奖励不另发 `ScheduleReceipt`，也不先给一个随机组件再用选择替换。旧补给和强化等日程资源仍用各自既有账本，其组件预算在 [LOOT](M8B_LOOT.md) 统一核算；不能在保底里把同一份资源再算一次。

## 3. 揭示、结算、选择与终局时序

### 3.1 战中只揭示，不中断战斗

M8B 采用明确的战后入库时点：Combat 按原规则运行；Match 依据本 tick 新的死亡事实，更新直接掉落和选择描述的揭示资格，保留完整来源事件。实际直接奖励在本轮战斗结束事务中统一授予。

战中不打开 `choice`，不发可操作的 `PendingChoice`，不让 UI 选项截停剩余战斗。已揭示的直接金币、装备、英雄此时尚未成为可用 Match 资源；不能临时改变已冻结的 Combat 快照。该时点选择属于本次补充政策，不能由 UI 的播放快慢决定。

### 3.2 战斗完成的一次事务

完成战斗时按以下顺序处理，保留 B2 的 loot → economy/growth → terminal 顺序：

1. 固定战斗结果、掉血依据、本战成长 delta、击杀／批准保底资格。可纯计算是否将终局，用于决定选择处理分支；此时不提前提交经济或 `gameOver`。
2. 完成最后一批揭示；所有未满足资格的直接掉落和选择描述成为 `forfeited`。不增加下一轮欠账。
3. 按冻结顺序授予已揭示的直接金币、装备和可入库英雄，资源与 `LootReceipt` 同提交。英雄仍先尝试原自动合并规划，确实无容量再记 pending。
4. 若本轮将终局，把本轮**已揭示且未解决**的组件选择按预冻备用项解决并真实授予；未揭示／forfeited 的选择不进入此分支。
5. 把本次英雄授予引起的升星谱系用于 §6 的成长归属，再一次提交本轮经济、XP、持久成长及结算收据。已授予金币计入本轮结算前金币；不能先按旧金币结算再补一次利息。
6. 终局按 B2 处理剩余满席英雄并进入 `gameOver`。非终局如有未解决的已揭示选择，打开第一项选择；否则回到 settlement，再处理待容量奖励的既有操作边界。

本轮经济只在步骤 5 结算一次。普通自选是在此后由用户命令完成，不回滚、不重算该轮收入、XP、成长或利息；自选只产生组件，避免在后续选择时再引入金币结算差异。

### 3.3 正常选择及满席英雄

正常非终局中，按 `dropId` 稳定排序一次展示一项组件选择，保留 finished Combat 快照，`returnPhase=settlement`。复用公开命令载荷 `selectChoice(choiceId, generation, definitionId)`；固定选择不刷新。`choiceId` 精确为 canonical JSON tuple `["m8b-loot-choice", dropId]` 的编码；复用 `PendingChoice` 时 `eventId=choiceId`、`generation=0`，与旧日程选择命名空间隔离。

该 `eventId` 仅关联组件选择来源，不使其具备旧日程事件或 `ScheduleReceipt` 的资格。Match 必须反查权威 pending choice 与描述账本识别来源，不能让客户端传入“本次来自 loot”决定发奖方式，也不能只检查一个字符串前缀就信任不存在的描述。

- 旧日程选择走既有日程处理；新掉落组件选择走 §2.4，只发 `LootReceipt`。
- 验证 choiceId、generation、合法候选、揭示资格和未解决状态后才分配 ID、写收据；失败返回原 state 引用且无事件、资源、ID 或 RNG 变化。
- 一项完成后才推进下一项；全部完成再回 settlement，不执行第二次 `settleRound`。
- `choice` 期间仍禁止普通运营。若同时有满席英雄，先完成组件选择，再在 settlement 使用 B2 允许的既有卖出命令释放空间，由领域自动重试入库。
- 未解决选择或未清 pending-capacity 均禁止 Continue。选择不会占备战席，也不要求先卖英雄才能完成，因而不会与容量等待互锁。

**复用命令载荷不等于复用原实现而无需改动。** 基线 `selectChoice` 目前总会为 component 创建 `ScheduleReceipt`，并重入旧日程；新分支必须明确绕到唯一 LootReceipt 授予事务。公开 protocol 仍为 2，无新领取命令，但内部状态、领域派发和验证确有增补。

### 3.4 提前终局和最终 6-7

正常 6-7 按 LOOT 只安排直接金币，没有自选槽位，不开运营窗口。其他任意回合因 HP 归零提前结束时，已揭示未解决的选择在同一战斗完成事务中使用备用组件，随后进入 `gameOver`；不是先进入终局再等待一次用户确认。

终局备用项仅决定**已经赚得的一件组件是什么**，不提供新的击杀资格、额外保底或未击杀补偿。它不改变 B2 对满席英雄 `retained-terminal` 的处理：英雄继续无收据、不计保底、不换金币。组件不占备战席，不能将它误送入英雄的终局保留分支。

## 4. 野怪机制的有限增补

机制、参数、站位和几何政策统一引用 [ENCOUNTERS](M8B_ENCOUNTERS.md)。优先复用 G01–G12 的效果执行与来源账本，不为每个野怪 ID 写一套战斗规则。

### 4.1 正式中立分类与同伴范围

M8B 野怪快照须有可验证的中立分类与遭遇 family 身份。提议的有限分类信息为 `unitKind=neutral`、`monsterFamily`，结合已有的单位 ID、队伍与 encounterId 判定同伴。分类来自冻结的内容定义；不能靠英雄名称、显示中文、ID 前缀或渲染素材判断是否是野怪。

同伴范围固定为同 encounterId、同队、同 monsterFamily 的开战成员，排除自身；成员集合在 combatStart 冻结，无需再提供任意群组脚本。具体 family 值、成员和所采用的有限被动／开场动作定义由 ENCOUNTERS 给出并参与内容 digest。不把后来的召唤物、其他遭遇／族或己方英雄自动视为同伴。

该分类也提供装备对中立目标的既有政策所需依据，例如 B2 的灼烧上限；不能在战斗中临时给所有 enemy 都套上“野怪”标记。来源仍保留完整 CombatOrigin，新的中立被动可使用正式内容定义所声明的 ability 来源，不以匿名 callback 执行。

### 4.2 同批死亡入口、回血与攻速

新增有限的“本批死亡事实”输入：由本批 HP 同步提交和原生死判定形成候选死亡集合，完成本批全部死亡清理后，再向同伴监听提交完整清单。清单每个单位只出现一次，并记录 combatId、tick、死亡单位 ID、队伍、遭遇／family 和可追溯事件身份。

这是供死亡监听使用的领域事实，不替代旧击杀／助攻归属，不把 `kill-or-assist` 重解释为“任意队友死亡”。一名死者的多个伤害来源或助攻不能触发多次同伴效果。原 `death` 事件及清理仍保持原顺序；新增正式事件类型或 Trigger 枚举的具体 TypeScript 映射须按本文已批准的有限语义接受代码评审，不能默默改其含义。

死亡监听只对**本批全部死亡清理后仍存活的同伴**登记后续反应；本批全灭时无人获得回血或攻速。一个持有者与一名死者的消费身份包含 combatId、holderId、完整被动 source key 与 deadUnitId，采用 canonical tuple；登记身份与反应计划原子提交，不能先排队后补 once。读取既有尸体、多个助攻、重复 step 或恢复不会再次消费。

| 招牌机制 | 通用执行部分 | 必须另明确的入口与时序 |
| --- | --- | --- |
| 石甲虫同伴死亡回血 | G06 的 requested／重伤后／actual／overheal 流程 | 死亡 tick t 登记有限反应；t+1 维护阶段只出队并生成待治疗计划，实际治疗在 t+1 原有伤害后存活治疗阶段执行 |
| 鸟同伴死亡增加攻速 | G01 攻速属性修饰＋G09 计数／消费记录 | 死亡 tick t 登记固定属性贡献；startsAtTick=t+1，在该 tick 维护中生效，不撤销已规划动作或重置已有剩余冷却 |

**不新增维护阶段治疗，也不回到 tick t 的治疗阶段补发。** 石甲虫的反应计划在 t+1 出队时不提前改变 HP；进入该 tick 原有 G06 治疗阶段后，仍须通过伤害后存活检查。若持有者在 t+1 的伤害批中已经被打至 0，本次治疗取消，不能把它从致死伤害中救回。每笔实际治疗请求在其 G06 执行位置按 ENCOUNTERS 的当前缺血取样，仍用既有 source key→targetId→packetId 顺序、重伤与封顶；同一幸存者的多个死者反应分别处理，不提前把两次缺血请求聚合。

反应计划至少保存原死亡事件身份、持有者和能力来源、目标、计划执行／生效 tick 及未执行／已执行／已取消状态。死亡事实按 deadUnitId→holderId 稳定登记；实际效果继续遵守所属 G01／G06 管线。来源执行前已死或战斗已结束即取消，计划不能留到下一场。鸟的 next-tick 以**原死亡 tick t**为基准；不能在 t+1 出队时再施加一次 next-tick 而推到 t+2。

有限反应调度本身也是新增入口：现有 `TriggerDefinition.effects` 不能承载任意 `AbilityOperation`，当前 Trigger 枚举没有正式死亡输入，不能靠将对象塞入原联合类型假装已支持。只补充本节的死亡反应计划、生命周期与一次消费验证，结果仍交现有通用效果执行器。

现有 `bulkyBuddies` 是旧技能侧专用逻辑，并且基线中立单位在该循环前被排除；它只能作为边界案例参考，不能直接宣布已提供新的 G09 通用死亡监听。

### 4.3 有限开场重定位与路径冲锋

狼的开场跳跃与先锋的开场冲锋需要有限重定位能力。现有 `TargetSelector` 负责选人，`AbilityTargeting.path` 负责命中路径，均没有修改占格的语义；现有 combat-start Trigger 的 Effect 列表也不是任意 AbilityOperation 的挂载点。

提议只支持 ENCOUNTERS 声明的两种开场一次动作。正式挂载点在双方常驻属性、初始装备和初始状态冻结后，第一次普通移动／动作前；读取共同开场单位与占用快照，统一规划并保留占格，再原子提交位置变化与领域 movement 事件。无飞行期、无任意中途传送、无自定义脚本；表现层可以播放跳跃或冲锋，但位置与行动时点只由领域决定。

| 有限动作 | 计划与占格规则 | 后续动作边界 |
| --- | --- | --- |
| 狼跳后排 | 狼按单位 ID 稳定处理；最远目标、后排相邻空格及换下一个目标的优先序均按 ENCOUNTERS；使用初始占用＋本批预约，不复用其他狼刚离开的起点；全部落点冻结后提交 | 无额外伤害、隐身或免控；无落点／无目标／已生效禁位移控制时记消费并留原地，不重试；位移后按 G10 正常重新选敌 |
| 先锋路径冲锋 | 开场快照选择最远目标；每步沿固定六方向顺序取首个严格靠近目标的邻格，抵达目标起始格后沿最后一步 axial 方向续行，直到 ENCOUNTERS 的总步数上限或边界；先冻结全路径，再取最远初始空格为落点并截断路径 | 可经过敌方占格但不推挤、不覆盖；只对截断路径上冻结的敌人各记录一次命中；无落点则消费能力、无位移／伤害／控制；实际伤害任务 executeAtTick=1，进入 tick 1 正常伤害批 |

先锋的目标 ID 列表按冻结路径位置顺序保存，执行时只对仍合法存活的既定目标出包，不因它后来移动就重抽新目标；具体伤害、取样和眩晕见 ENCOUNTERS。任务沿既有 `ActionTask` 的延迟执行、来源死亡取消及控制取消政策；来源在执行前死亡或已生效控制取消时，不发伤害／控制包，**已经提交的位移不倒退**。控制仍按 B2 从伤害发生后的下一 tick 生效。

开场计划至少保存来源／一次身份、初始起点与瞄准目标、有限冻结路径（狼无需路径）、预约落点、实际 from／to、动作消费结果；先锋另保存唯一后续任务及其执行／取消结果。移动成功与伤害任务完成是两个状态，不能用一个 `consumed` 布尔值把“位移已完成、伤害待执行”丢掉。恢复已有战斗不得重新规划、重新预约或重新位移，也不能漏掉尚未执行且未取消的任务。

几何、镜像后排、候选并列、占格失败和首次行动时点以 ENCOUNTERS 的精确定义及手算向量为准。所有落点必须在界内且不重叠；补充能力只开放这里声明的有限参数，不能扩成玩家运营位移命令或任意战中传送系统。

### 4.4 龙的有限四格锥形

ENCOUNTERS 已明确采用方向性有限锥形，不能替换成主目标的一格邻域或 radius 圆区。新增的只是以下受限六角格选择入口：以本次普攻冻结的龙起点和主目标格，按 E、SE、SW、W、NW、NE 固定顺序取首个严格靠近主目标的方向 d，并转换为 axial 向量。

候选格恰为 `primary+d`、`primary+2d`、`primary+d+dLeft`、`primary+d+dRight`；dLeft／dRight 为 d 相邻的两个六方向。越界格丢弃、排除 primary，仅从这些格的存活可选敌人中按距 primary→单位 ID 取最多 2 个次要目标。主目标位置缺失时无溅射，目标集合在该次动作完成时冻结，每个目标最多一个副包。不得用不同 row 的 offset 差值直接代替 axial 方向，也不接受 UI 角度、像素或任意多边形输入。

只有目标集合生成是新增部分。副包金额使用主攻击本次已经取样的 AD 和 ENCOUNTERS 的比例独立取整；副包为 physical／ability-direct／critEligibility=never，保留原 rootActionSeq 和父普通攻击身份，不继承主包暴击、不再抽词、不再发 attack-completed／incoming-basic-hit，也不递归触发自己的溅射。其余伤害、抗性、防止、护盾、来源和触发资格继续交 G02 及冻结矩阵；不在动画结束回调中结算。

### 4.5 中立攻速必须有实际消费者

基线 `interval` 对 neutral 直接返回固定 `attackIntervalTicks`，不会消费攻速修饰。因此“给鸟加一条 G01 修饰”不足以让攻击变快。

M8B 新中立模板以 ENCOUNTERS 的整数 `baseASBps` 为唯一基础攻速输入，统一按 G01 计算实际攻击间隔：`max(1, ceil(2000000000 / (baseASBps × (10000 + sumBonusBps))))`。ENCOUNTERS 同列的基础 attackIntervalTicks 是零修饰时的推导校验值，不是另一份可独立调整的输入；不从旧整数间隔反推攻速，也不先取整 effectiveAS 再计算最后的 ceil。所有输入与中间量继续遵守 B2 安全整数／有理数及合法攻速范围约束。

具体基础值以 ENCOUNTERS 为准。保留旧守卫作基线场景时，继续其既有整数间隔；不把新模板的解释方式反向覆盖旧内容。验证至少包含新模板无修饰时与声明校验间隔一致、叠加后下一次新攻击使用新间隔、正在等待的剩余冷却不因增益而被重置，以及 UI 读到的攻速与实际攻击节奏来自同一权威状态。不得为演示鸟的变快另设渲染计时器。

### 4.6 中立基础暴击的编译、投影与恢复

审计 A1 指出的基线差异成立：`spellCrit()` 在缺少显式投影时为 neutral 使用 0 基础暴击率；`validateM5Runtime` 也把 neutral 的合法概率固定为 0。`UnitDefinition`／`ResolvedUnitStats` 当前缺少基础暴击输入，开场编译没有从新中立目录传入该值。因此仅在 ENCOUNTERS 写 `2500Bps/14000Bps`，或只手动给 CombatUnit 填一份投影，都不能完成接入。

本增补需要贯通三段边界：**B3/G03 预留单位基础暴击输入与编译通路 → B7 从已签收中立内容生成开场投影 → B9 按同版本解析内容及合法来源验证恢复结果**。基础暴击率／倍率必须随内容定义、解析属性与开场快照传递；实际字段归属按已批准边界在目录类型的代码评审中确定，不能藏成按单位名称分支的常量。具体数值及七类候选／五种小兵的来源差别以 ENCOUNTERS §3 为准，不把它们描述为旧中立运行规则。

现有 G03 已可表达该投影：没有技能暴击授权源的新中立模板，等价于 `authorizeSpellCrit([], [], 2500, 14000)`，得到 `chanceBps=2500`、`multiplierBps=14000`、`enabled=false`、两组授权来源为空、`redundantItemBonusBps=0`。这表示 **basic 普攻可按基础概率暴击，技能仍未获授权**；不能伪造 item／nonItem 来源或打开 enabled 来让普攻暴击。龙的 `never` 副包与先锋的 `never` 伤害不因该基础值获得暴击资格。

恢复器应核对冻结内容版本、该 definition 的已解析基础值、合法修饰／授权来源及最终投影，不能只把旧判断改成“所有 neutral 都允许 2500”，也不能只把全局 neutral 的 0 默认值直接替换为 2500。旧守卫基线继续按其原内容保持 0；新内容缺字段或不匹配时明确拒绝，不能默默回落到旧 0 值。恢复与查询消费 0 个词，不重新抽已完成攻击。

独立验收向量 **A1-CRIT**：新远古龙本次已取样 AD=85，攻击者无其他属性修饰；主目标和合法次目标护甲为 0、生命足够，无增伤／减伤、护盾、完全防止或转移。为该唯一已规划普攻指定下一个暴击 `word=0`（不是 seed=0），普攻应得到 `floor(85×14000/10000)=119`，只消费 **1 个战斗词**。合法次目标若存在，每个仍是 `floor(85×3500/10000)=29` 的 `never` 副包，不继承主包暴击、不再耗词。在该攻击前保存再恢复，与连续运行的 119／29、事件、投影和 RNG state/draws 完全一致；攻击后恢复不重复伤害或抽词。相同条件的旧守卫仍按其 0 概率执行非暴击普攻。该向量只验证输入接通，**不修改 G03 的判定、取整、抽词或技能授权公式**。

### 4.7 零蓝内容的导入与运行边界

ENCOUNTERS 的新模板均声明 `initialMana=0,maxMana=0`。G08 已规定 `maxMana=0` 的无蓝单位法力请求 `applied=0`，但当前 [`validateUnitDefinitions`](../src/simulation/units.ts) 的下限是 1；因此 B7 不能只新增目录记录而沿用旧校验，也不能用 `maxMana=1` 的占位值绕过。

B3/G08 明确接受的输入边界，由 B7 的导入、目录与解析属性校验贯通到开场快照，再由 B9 按同版本内容恢复校验：合法无蓝定义须为零初始／上限法力，招牌由已声明的被动／开场入口执行；不能把零门槛解释成每 tick 免费施法。负数、非整数、`initialMana>maxMana` 仍拒绝，也不因中立零蓝放宽未声明的英雄或其他资源类型。

独立验收向量 **A2-MANA0**：合法新中立定义以 0/0 成功导入、解析和开战，尝试请求 10 法力仍 `applied=0`、当前法力为 0，不生成虚假施法或 CastReceipt；`initialMana=1,maxMana=0` 的目录拒绝。保存／恢复保持相同零蓝投影及任务状态，0 额外 RNG／法力。这里只接通 G08 已有语义，不重新定义回蓝、锁蓝、溢出或施法完成规则。

## 5. UI、序列化与回放的必要适配

### 5.1 UI 仅显示领域已经确认的事实

原 `RevealedDropView` 要求具体 payload 且 `allowedActions=[]`，不直接容纳一个未解决的选择机会。应新增选择奖励的只读投影，或由现有 `PendingChoice` 展示当前可操作项；不能把未知组件显示成已授予物品，再由 UI 自行替换。

领域查询应能区分：隐藏计划、战中已揭示待结算、战后待选择、已授予、满席待入库、终局保留。只有真正已授予者显示实际 receipt 与物品／英雄身份。未满足资格和未用到的备用组件不暴露给准备期预览。

选择期间 Continue 与普通运营是否可用、满席原因、终局不能操作等都由 Match 查询给出。未解决自选须有明确的待选投影与阻塞原因，不能为了适配旧 `pending-capacity`／`bench-full` 分支把它伪装成英雄容量问题；现有 UI 合同缺少的只读形状需作为增补提交。界面不另算保底、掉落概率或下一份奖励。本文不规定布局、颜色、动画等视觉实现。

### 5.2 选择来源路由和恢复校验

当前恢复器把 component 选择限定为旧日程事件且要求恰好 7 个候选。M8 新验证器必须区分日程来源与掉落来源，使用冻结的 8 组件池；不能为了“兼容”放宽成任意字符串或任意数量。

最小校验包括：

1. 直接掉落与选择描述的身份唯一、所属 round／encounter／source／slot 正确；poolVersion 在本规则版本中存在，备用组件属于精确的 8 项池。
2. 每个选择的资格、解决记录与 LootReceipt 一致；未揭示、forfeited 或已解决的项不得再次 pending。实际选择 payload 为数量 1 的合法组件；备用解决时 definitionId 必须等于预冻备用项。
3. `PendingChoice` 与当前最早可操作的已揭示未解决项完全对应；choiceId／generation／候选集合／返回阶段有效。战斗运行中不出现可操作选择，gameOver 不保留待选项。
4. 各 RNG state／draws、计划抽样顺序与备用项一致；恢复只验证与重建视图，不抽新词、不退词、不发奖励。
5. `LootReceipt` 与实际授予身份及保底计数对应；合成或升星后被消费的历史实例可以不再存在，但必须有合法消费／升级谱系，不能因此补发。
6. 满席英雄没有授予收据；retained-terminal 没有可操作动作、不折金币、不计英雄领取；未解决选择不能借英雄的终局保留状态蒙混过关。
7. 野怪 family／同伴集合／被动来源、死亡消费及 t+1 反应记录、开场重定位结果与后续任务、有限锥形目标、攻速叠层和生效时点均有合法内容依据；恢复不能提前治疗、重复位移或丢弃合法待执行任务，不可把任意 JSON 往返当作验证通过。
8. 结算历史和成长回写收据保持一次性，不能在选择确认、容量重试或恢复时产生第二次经济／成长提交。
9. 第一阶段档案按 OPENING 与显式 `RoundDefinition` 验证：允许合法的等级 1／2、三场 1-2～1-4 与其 2/3/5G、2/2/0XP；全局采用 38 推进轮／33 战的明确日程。不能继续使用旧恢复器的最低 3 级、最多 35 轮、统一每轮 2XP 或旧序号公式，也不新增可保存的 1-1 中间 phase。
10. 新中立基础暴击、基础攻速与零蓝值必须匹配同版本的声明内容和解析投影；不能继续要求所有 neutral 暴击率为 0，也不能仅放宽白名单而跳过来源验证。基础普攻概率不等于技能授权，恢复不得自动补授权、重算为旧固定间隔或把 maxMana 改成 1。

这是结构一致性与确定性重演验证，不声称在没有完整命令历史时能证明所有历史输入都真实发生过。

### 5.3 事件与版本

实现时须补齐 Match 领域的掉落揭示、实际授予、选择解决记录及相应事件定义，携带原 drop／receipt 身份；既有 `choiceOpened`／`choiceSelected` 可保留原载荷。不得借旧 `rewardGranted` 名称静默把它的 `ScheduleReceipt` 载荷换成 `LootReceipt`。

Combat 的新死亡批次输入、开场重定位和有限几何执行应保留完整来源、tick／序号、实际目标及一次消费状态。原战斗伤害、死亡、成长事件仍保留当时 Combat 单位身份；后续 Match 升星不改写过去的事件。

## 6. 掉落英雄升星后的成长归属

### 6.1 问题与保留顺序

M8B 的英雄掉落可能在战斗完成时触发自动升星，而 B2 明确掉落处理在持久成长回写之前。此时准备区的旧单位 ID 可能已被合并消费，本场 Combat 的成长 delta 仍绑定原 ID。直接沿原 ID 回写会复活已消费条目的成长，或让 survivor 丢掉一部分成长。

不改成“先回写成长再发英雄”来规避问题。应复用已有 [`unitUpgraded`](../src/simulation/upgrades.ts) 的 survivorId／consumedIds 事件谱系，将**已存成长**与**本场尚未提交的 delta**分别沿同一谱系迁移，最后才提交本战成长。

### 6.2 一次领域事务内的归属规则

1. 从本场完成的 Combat 冻结每个原始单位的新增成长 delta；它不包含 Match 中已经保存的存量成长，也不因本场失败或单位死亡而丢失。
2. 按原授予和自动合并顺序处理英雄奖励，保留每条 `unitUpgraded` 的 survivor／consumed 谱系。新掉落的一星英雄初始成长为 0。
3. 每条升级事件同时将当前存量账本和待提交 delta 账本中 survivor＋consumed 的值归并到 survivor，并删除 consumed 键。级联合并继续沿后续事件迁移，不只处理第一层。
4. 掉落与合并处理完毕，在 B2 规定的成长回写位置，把已迁移的本战 delta 加入当前存量账本，按唯一 combatId 只提交一次。不能再遍历原 Combat ID 补加第二遍。

不改 survivor 选择顺序、不改装备／异常迁移或三槽规则，也不把原始战斗事件中的来源 ID 改成新 survivor。英雄授予收据记录真实授予与消费链；被授予的候选 ID 即使立即被合并消费，也不是“未领取”或可以再次授予的理由。

### 6.3 独立手算向量

同一英雄的 A、B 已存成长分别为 100、200 Bps，本场 A、B 新增分别为 30、40 Bps。第三张奖励卡 R 的成长为 0；掉落触发升级，按原保留规则 A 为 survivor，B 与 R 被消费。

- 存量归并到 A：100＋200＋0＝300 Bps。
- 本战 delta 归并到 A：30＋40＋0＝70 Bps。
- 最终 A：300＋70＝**370 Bps**；B、R 不再有持久成长条目。

不能得到 300、330、340，也不能一边给 A 370 一边留下 B 的 40。若 A 随后在同一事务的级联合并中又被 C 消费，则其 300 存量与 70 待提交 delta 均继续归 C，最终仍只加一次。

满席未入库英雄没有授予或升级事件，不改变此谱系。若其在本轮经济和成长已经结算后，由后续卖出／合并释放空间才入库，使用此时已存的成长执行既有合并迁移即可，**不能重新应用本战 delta**。终局 retained-terminal 英雄不触发隐含升星。
