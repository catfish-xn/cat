## 已确认的问题

固定 f58c9fe 的每 tick 复制会反复遍历单位携带的静态技能、装备程序、来源和触发定义。原生 `structuredClone` 自身占两种 9v9 CPU 剖析约 25%，单位复制入口还占大量自身采样。移除重复的触发采样和第二次单位展开后，同机 30 seed 仍未达 5/10 ms。新的无原型临时对象试验收益不稳定，已撤回实现并保留结果。

## 最小拟议范围

优先只研究引擎在构建/恢复边界自产且已完成现有校验的 `itemPrograms` 与 `sources`，不直接扩大到全部技能/机制对象。在 seed1、tick40，18 个单位原克隆载荷按 JSON 字节近似为 181,657 / 186,351 B，两字段合计 116,883 / 116,708 B（distinct / mirror）；这是大小代理，不能当作时间收益。对应原始记录归档为 [copy-inventory.json](evidence/m8-node3/copy-inventory.json)。

拟深度冻结这些自产静态定义并标记为可信，tick 内允许共享。HP、位置、mana、运行计数、状态、任务、护盾、账本仍按原语义更新。外来对象、替换过的定义、未验证输入必须走原 native clone/验证路径；不能仅凭对象长得像 JSON 就信任。

必须先界定静态定义与动态数据之间允许的引用关系，避免把原来一起复制的别名拆开。不得冻结或共享整个战斗状态来偷减工作，不得丢事件、删装备、改规则、改 RNG、放宽 5/10 ms 或减少非法输入覆盖。

## 为什么需要决定

该方案会改变部分返回对象的物理可写性（冻结）及跨 tick 引用身份。现有 TypeScript 类型为 readonly，但 B8/Q1 已明确要求保留公共 step 的 native clone 语义，见 `tests/m8-b8-copy-semantics.test.ts`。不能把它当作前两项同语义微优化直接落地。用户本轮要求“遇到必须改变规则或合同的方案再交我决定”，因此冻结/共享边界需先明确。

选项：

1. **允许设计并验证受保护的静态定义冻结/共享边界（建议）**。先补合同说明与反例，再做独立提交、完整等价/拒绝对照和同口径测量；不预先承诺达到预算。
2. 保持现有逐单位 native clone 的可观察行为，不扩大共享范围。保留已验证的两项收益，节点三仍未通过；继续寻找其余不改变复制边界的优化，无法承诺 5 ms。

若选择 1，测试必须至少包括：外部替换定义后非法输入仍拒绝；Date/稀疏数组/函数拒绝/访问器读取顺序保持；循环和跨字段别名；冻结的历史输入不变；原 60 场 9v9 完整状态/事件、公开回放、44 件装备保存/恢复及所有既有断言。任一反例未解决都不能合入现有功能候选。
