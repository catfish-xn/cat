## 接口、结算与恢复

- 新内容在强化／异常注册表接线；三个意志在团队属性层处理；溢流使用共同散件实现；支持装备覆盖以持有者的实例生成光环，不修改全局物品定义。
- `p2GiftPlan` 按拥有的强化确定赠品身份；`drainP2Gifts` 使用既有 `grantMechanicItem` / `grantMechanicUnit`。英雄透传同一事务的 `UnitLootPolicy`；池空按费用折金，满席保留同一待领计划，卖出／领取／既有奖励重试入口继续领取。每笔使用独立唯一收据与资源来源。
- `validateP2Gifts` 将每笔新增赠品与强化权威、具体物品／英雄及实际赠送轮次相连；拒绝错误定义和额外收据。普通物品赠送不可缺失。
- `CombatUnit.s13P2Opening?` 是只在开战写入的随机选人及已广播数值事实；不改变准备棋盘。恢复在所有数值消费者之前，用可信开战输入和战斗种子独立重演，逐单位比较此字段；原有来源、触发器、HP、运行时、RNG 与结算校验全部保留。
- 数值读取由既有 `readCombatStats` 统一输出；AD/AP 采样候选与最大生命基底校验计入经过认证的开场加成。
- 六个重点项各有征服者 0→2、化学男爵 0→3 的双边战斗用例，共 12 条。经真实选择、部署、`snapshotForBattle → compileBattle → resolveTwoSidedBattle → proposeSettlement → applyRoundSettlement` 提交；旧档位收据被拒，当前档位收据成功且重复提交不重发。

## 自行决定

- 战斗随机使用现有 Combat lcg32 流，在既有开场初始化、羁绊与光环后执行；按阵营／强化／选择身份排序，每个被选单位消耗一词，候选少于名额时只抽实际人数。精心赋能与三项赛共用同一无放回选择程序。
- 获得英雄的随机计划使用 seed、席位及 choiceId 经 FNV-1a 命名空间派生的独立 lcg32 流；均匀有放回抽取对应费用完整商店池，不改变商店／选择／奖励主流。满席重试不重抽。
- 分享 AD 按固定值加在接收者百分比 AD 结算之后；AP、双抗与生命按现有属性层约定处理，每项先向下取整。三个溢流仅强化仍为对应散件的实例。
- 扩池后保留独立字面目录 oracle，并补齐赠品来源、英雄谱系、物品守恒与收据校验。历史 G2-3／G2-augments 目录保持原字节；变更的是当前 oracle 与 G2-4b 的现行指纹。
- 原有恢复测试改用能够通过正常金币抽到目标异常的固定种子（吸收 3、鹰眼 0），并通过真实卖出释放隔离测试需要的容量；原断言、测试数量、时限与校验不减少。

验证结果和指纹检查见本目录 `validation.json`。
