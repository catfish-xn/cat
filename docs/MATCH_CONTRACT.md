# M4 Match contract v4

Public entrypoint `src/simulation/match.ts`; readonly types `match-types.ts` and `strategy-types.ts`. Pure commands, explicit RNG/IDs and single settlement ownership remain. [M4_RULES](../M4_RULES.md) defines the numerical and ordering contract; this document describes the API boundary.

- `createMatch(seed=42)` validates uint32 including zero and returns a separate JSON-serializable schema4/rules m4-v1/content m4-slice-v1 state. The canonical content digest includes units, abilities, all strategy catalogs, schedule, shop and enemy curve. Persistent state includes items, augments, one optional Anomaly binding, pending choice, schedule receipts and three explicit RNG streams.
- Existing buy/sell/reroll/deploy/start/continue signatures remain. New `buyXp(state)` takes no price/amount from UI. Success returns `{ok:true,state,events:MatchEvent[]}`, with unitUpgraded events for each merge. Rejections return `{ok:false,state,reason}` with the identical original state and no partial money/XP/RNG/ID/roster writes.
- `validateMatchDeployment(state,id,target)` is shared by preview and commit. It adds phase/population to unchanged GameState geometry and permission rules. Moving a board unit does not consume another population slot. Start rejects over-cap preparations.
- Preparation alone permits economic and deployment commands. F rejects in order wrong-phase, max-level, insufficient-gold; F never changes existing shop/generation/RNG. Only initial shop, successful D and Continue consume RNG, ten words each.
- Buy checks generation and purchased status before resources, then plans purchase+recursive triples atomically. Full bench is checked on the final plan. New candidate IDs consumed during merging are still never reused. Prices derive from definitions and star, never from UI.
- `combineItems`, `equipItem`, `selectChoice`, `selectAnomalyTarget` and `rerollAnomaly` are synchronous atomic commands. Two inventory component IDs produce one new item ID; equipped components never auto-combine. Equipment location is authoritative in `items`, with slots 0–2. Upgrades preserve survivor slots, transfer consumed units' equipment deterministically and return overflow to inventory. Sales return all equipment and destroy a binding on the sold unit.
- `choice` is a Match phase. Every ordinary economic, item, deployment, Start and Continue command rejects until the pending choice completes. Choices validate choice ID and generation before committing. Augments persist on the Match; Anomaly locks one owned target before offers are drawn, costs 2G per reroll and follows the survivor on upgrade. Selecting is free and consumes no RNG.
- Shop, choice and reward streams are independent. Three-item partial Fisher–Yates draws exactly three words, with sorted eligible content IDs. Rerolls exclude the immediately previous three choices. Schedule drains ordered automatic rewards and stops at the first unresolved choice; receipts prevent repeat grants. Absolute round remains authoritative; stage labels are derived.
- `stepMatch` consumes one50ms combat tick. Only terminal transition commits income/XP/HP/history. HP0 enters gameOver; otherwise settlement. Empty player deployment with enemies may start and immediately settle enemyWin at tick0; low-level validateCombatStart still reports missing-player for diagnostics.
- `nextRound(state,expectedRound)` only accepts a current settled round; no repeated reward. It refreshes shop using the already updated level, replaces enemy preparation, preserves player resources and positions, discards combat, then drains the next round's schedule. Game Over does not grant next-round rewards.
- GameOver rejects all normal commands including Continue. Outside combat, step returns identical state and no events. New Match discards the entire old match. Rendering never settles, calculates money, or repairs state.
- MatchSession delegates synchronously and holds only current MatchState plus fixed-step accumulator. Phase changes/finish/new match clear time remainder. Native D/F/E and pointer actions commit in event order, with no animation gate.
- `serializeMatch` and `restoreMatch` validate plain JSON, exact versions/digest, references, unique ownership, receipt/history consistency, phase, normalized economy and Combat snapshot/runtime. Restore never runs combatStart or redraws a choice. Old versions reject explicitly. This validates a structurally consistent local save; it is not a cryptographic proof of its command history.
- Match-domain events have their own monotonic sequence; Combat events retain combatId/tick/eventSeq, starting at zero per battle. Rejections consume neither sequence. Replay compares every command/tick state and all events; browser observers retain the complete current-battle ledger including Start's tick-zero events.
